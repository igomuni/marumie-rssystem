# Opus 5 向けプロンプト統制の対応案

## 目的

Claude Opus 5 の公式プロンプトガイドで挙がっている「チューニングが要る挙動」に対し、本リポジトリの
プロンプト面（`CLAUDE.md` / `.claude/CLAUDE.md` / `.claude/commands/*.md`）で統制できる箇所を洗い出し、
具体的な改修案を提示する。エージェントの出力が冗長化する・スコープが勝手に広がる・不要な自己検証や
サブエージェント起動でトークンが浪費される、という状態を防ぐため。

出典:

- <https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5>
- <https://www.anthropic.com/news/claude-opus-5>

## 前提: ガイドが言っている要点

| # | Opus 5 の挙動 | 推奨される対処 |
|---|--------------|--------------|
| G1 | ユーザー向け応答が従来 Opus より長い。effort を下げても**表示される応答長は縮まない**（effort が制御するのは思考量） | 簡潔さを**明示的にプロンプトで指示**する。長いシステムプロンプトでは末尾に短いリマインダを併置 |
| G2 | エージェント作業中のナレーション（実況）が多い | 更新の**頻度と形**を明示（着手前1文 / 重要な発見と方針転換時のみ / 完了時は結論から） |
| G3 | ディスクに書く成果物（レポート・Markdown）が長くなりがち | 文書長のキャリブレーションを明示（水増し禁止） |
| G4 | 言われなくても自己検証する。「検証ステップを入れよ」「ダブルチェックせよ」の指示は**過剰検証を誘発する** | 既存の検証系指示を**削除**する（品質は落ちずトークンだけ減る） |
| G5 | タスクのスコープを自分の判断で広げがち | 「指示された範囲を、指示された粒度で」を明示 |
| G6 | サブエージェントに委譲しやすい。小タスクへの委譲はコスト増 | 委譲して良い条件を明示、または起動数に上限を置く |
| G7 | 自己訂正のナレーションが多い | 「ユーザーの判断が変わる誤りだけ訂正、それ以外は黙って直す」 |
| G8 | コードレビュー精度が高い。ただし「重大な問題だけ報告」と書くと**字義通り報告を絞る** | 全件report → 別パスでフィルタ、という構成にする |
| G9 | effort `low`/`medium` が費用対効果的に強い | 日常作業は低め、難しいエージェント作業は `xhigh` |
| G10 | thinking 無効時のみ発生するアーティファクト（tool call のテキスト漏れ・XMLタグ漏れ） | Claude Code は thinking 既定 ON のため**本リポジトリでは対象外** |

## 現状の棚卸し

- `CLAUDE.md`（70行）: アーキテクチャ・レイヤー規約・PR運用。**応答スタイルの統制は皆無**（G1/G2/G3/G5/G7 が無防備）
- `.claude/CLAUDE.md`（22行）: ファイル操作制約・探索の規律・Markdown 記法。
  「既に文脈がある作業のためにサブエージェントを新規起動しない」は**すでに G6 に沿っている**（強化のみ）
- `.claude/commands/plan.md` step 5「…矛盾していないか**ダブルチェック**する」 → **G4 に真っ向から抵触**
- `.claude/commands/plan.md` の「今後の展望を書かない」「工数見積を書かない」 → G3/G5 に沿った良い既存ルール
- `.claude/commands/review.md`: 「重大な問題だけ」等の絞り込み表現は無い → **G8 は現状 OK**
- `.claude/commands/quality-check.md`: lint/tsc/test の実行手順であり自己検証指示ではない → **変更不要**

## 対応案

優先度は 効果/リスク比。A = 今すぐ入れたい、B = 入れると良い、C = 様子見。

### A-1. `CLAUDE.md` に「応答スタイル」節を新設（G1 / G2 / G7）

`## Agent の行動ルール` の直前あたりに追加する:

```markdown
## 応答スタイル

- **簡潔に。** 主要な答えに文字数を使い、前置き・注意書き・まとめの再掲は短く。説明を求められたら
  まず要点を述べ、詳細な解説は明示的に求められたときだけ書く。
- **作業中の実況は最小限に。** 最初のツール呼び出し前に「何をするか」を1文。作業中は重要な発見か
  方針転換のときだけ短く報告する。完了時は結論（何が起きたか / 何が分かったか）を第1文に置き、
  根拠や詳細はその後に書く。
- **自己訂正のナレーションを絞る。** 先の発言の誤りは、ユーザーのコード・結論・判断が変わる場合だけ
  訂正する。影響のない言い間違いは黙って直して先に進む。
```

### A-2. `.claude/commands/plan.md` step 5 のダブルチェックを削除（G4）

現状:

```text
5. **整合性チェック**: 作成したドキュメントが CLAUDE.md のレイヤー設計ルールと矛盾していないか
   ダブルチェックする。特に以下を確認する：
   - scripts/ にUIロジックが含まれていないか …
```

案: step 5 を丸ごと削除し、チェック観点は step 4（ファイル作成）の中に「設計は CLAUDE.md の
レイヤー規約に従うこと（`scripts/` にUIロジックを置かない、`app/lib/` に HTTP/React を持ち込まない、
`client/components/` から直接APIを呼ばない）」という**制約**として書き下す。
「作ってから見直す」を「作るときの前提」に移す形で、検証パスを1回減らす。

以降のステップ番号（6 → 5）を繰り上げる。

### A-3. `docs/tasks/*.md` の長さキャリブレーション（G3）

`.claude/CLAUDE.md` の「回答の出力先」項に1行足す:

```markdown
- **task doc の長さは中身に合わせる**: 必要な実質だけを書き、水増しの節・重複するまとめ・
  定型の前置きを足さない。
```

本リポジトリは task doc を大量生産する運用（INDEX.md 参照）なので、G3 の影響が最も出やすい箇所。

### A-4. スコープ統制を `CLAUDE.md` の行動ルールに追加（G5）

```markdown
- **指示された範囲を、指示された粒度でやる。** 定型的な判断は自分で決めてよいが、解釈違いで
  成果物が大きく変わる場合だけ確認を取る。依頼が誤っていると思ったら1〜2文で指摘したうえで、
  依頼どおりに進める（黙って範囲を狭めたり広げたり作り替えたりしない）。着手した範囲は最後まで
  終わらせ、できなかった部分は明示して報告する。
```

既存の「PR は許可なく作成しない」と方向が一致しており、衝突しない。

### B-1. サブエージェント統制の明文化（G6）

`.claude/CLAUDE.md` の探索の規律にある既存1行を、条件付き許可＋上限の形に書き換える:

```markdown
- **委譲の基準**: 多ファイル横断の広域調査など、独立して並列化できる大きめの調査だけ Explore
  サブエージェントに委譲し、本会話には結論だけ持ち帰る。数回のツール呼び出しで自分で終わる作業は
  委譲しない。自分の作業の検証・再確認のためにサブエージェントを使わない。1体で足りるなら1体に
  留め、起動数を増やさない。既に文脈がある作業のためのコールドスタートは避ける。
```

### B-2. `/review` の報告方針を「全件出す」と明示（G8）

現状の `review.md` に絞り込み表現は無いが、Opus 5 は逆に「全部出して」と言われた方が精度が出る。
step 3 の冒頭に1行:

```markdown
気づいた問題は重要度で切らずに全件挙げ、そのうえで「要修正 / 改善提案」に振り分けて報告する。
```

### B-3. `.claude/CLAUDE.md` 末尾に短いリマインダを置く（G1 補強）

ガイドは「長いシステムプロンプトでは末尾に短い再掲を置く」ことを推奨している。
`CLAUDE.md` + `.claude/CLAUDE.md` + skill 本文で合計が長くなるため、`.claude/CLAUDE.md` の最後に:

```markdown
## 出力の既定

簡潔に。実況は最小限。書き物は必要な実質だけ。
```

### C-1. effort の運用（G9）

プロンプトではなく運用レベルの話。ファイル改修は不要だが、目安として:

- 日常の実装・修正・調査 → 既定（`high`）のままで良いが、単純作業は下げても品質は保たれる
- 大規模リファクタ・複数ファイルにまたがる機能追加・Sankey のレイアウト改修 → `xhigh`
- `/code-review ultra` は既定の設定に従う

`/fast` はモデルを落とさず出力を高速化するだけなので、品質面の懸念なく使ってよい。

### C-2. 対象外（G10）

thinking 無効時のアーティファクト（tool call のテキスト漏れ、`<thinking>` タグ漏れ）は、
Claude Code が thinking 既定 ON で動くため本リポジトリでは考慮不要。
「考えるな」「推論するな」系の指示を将来書かないこと、だけ守れば良い。

## 実施記録（2026-07-26 実施・完了）

A 群・B 群をすべて適用した。C 群はファイル改修を伴わない運用方針のため対象外。

- `CLAUDE.md`: 「応答スタイル」節を新設（A-1）、「Agent の行動ルール」冒頭にスコープ統制を追加（A-4）
- `.claude/commands/plan.md`: step 5「整合性チェック（ダブルチェック）」を削除し、
  レイヤー規約を step 4 の**制約**として書き下した。以降のステップ番号を繰り上げ（A-2）
- `.claude/CLAUDE.md`: task doc の長さ規定（A-3）、委譲基準の書き換え（B-1）、
  末尾に「## 出力の既定」リマインダ（B-3）
- `.claude/commands/review.md`: step 3 に「重要度で切らず全件挙げてから振り分ける」を追加（B-2）

## 検証方法

プロンプト改修は定量評価が難しいため、次の観察で判断する:

1. A 群を入れた直後の数セッションで、完了報告が結論から始まっているか
2. 新規 `docs/tasks/*.md` の行数が既存の平均より膨らんでいないか
3. `/plan` 実行時に「ダブルチェックします」系のステップが消えているか
4. 小さな調査でサブエージェントが起動されなくなっているか

問題が出れば個別に巻き戻す（各案は独立しており、部分適用できる）。

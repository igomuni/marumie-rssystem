# MHLW文書階層PoC 結果（v1）

実験契約は `20261002_2141_MHLW文書階層PoC_実験計画.md`（実装前に固定）。ここでは結果・限界・判断だけを書く。

## Hypothesis

総表と明細の見出し構造（左端コードの形・xインデントの階段・文書順）を、ページをまたいで追えば、組織→項→要求の親エッジを、GT・コード値lookup・凍結層なしで復元できる。過年度表など見出し形状を持たない行は親にならない。

## Method（要約）

SourceToken → TableGeometry → LogicalRow だけを入力に、先頭tokenの形で見出し候補を拾い、view ごとにkey tokenのxを単一連結クラスタリング（隣接差 ≤ 0.25×フォントサイズ、支持2行以上）して階段の順位をlevelとし、文書順のstackで親候補を決める。親が確定できなければ unresolved / level_gap。GTは評価CLIだけが読む。実装・仕様は `docs/data-pipeline-v2.md` の DocumentHierarchy PoC 節。

## Development / holdout

development=組織070の部分木（拡張GT 16ノード・15エッジ、うち research GT 8ノード・7エッジ）、holdout=組織080の部分木（21ノード・20エッジ、うち research GT 3ノード・2エッジ）。評価は拡張GTと research GT 部分集合を分けて集計。**開示**: 計画固定前の探索で holdout の先頭（p20 と p1603 の見出し行）を目視していた。p1604–p1700（要求196–206・項015–045）は未観察。

## Observed hierarchy evidence

- 明細の見出し格子は x=51.8 / 58.7 / 65.6 / 72.5 / 79.4（約6.9pt=約1em刻み）。総表は 62.1 / 65.6 / 69.0（約3.45pt=約0.5em刻み）。要求は「要求番号（x≈34–36）+ NN-NN」で、コードの位置が階段の level 3 に当たる。
- 親見出しが再掲されない要求がある（物理p1595の189、p1600の193 など）。stackは間の行を越えて前ページの親に辿り着いた（要求189は235行、193は130行、項は最大4,044行）。
- p1555 の項（010）と要求（186）の間にある過年度表・罫線表（論理行13–33）は、見出し形状を持たず、どのedgeにも現れない。
- 総表の頁数列（4桁だけのtoken）が、目次の開始頁と一致した（summary の照合は printedPageRefCandidate == 目次の頁）。

### 評価側の修正（開示）

初回の評価では detail の development が 13/15（false parent 1・not found 1）だった。原因は**推論ではなく評価側の照合**で、p1587 に同じコード `011` の見出し行が2つ（項の見出し x=58.7 と、別の見出し行 x=79.4）あり、候補が2件で「見つからない」になっていた。推論artifactは変更せず、候補が複数のときだけGT名称との前方一致で絞る tie-break を評価側に追加した。修正前は `--no-name-tiebreak`（`evaluation-v1-basic-matcher.json`）で再現できる。この修正は推論ルール・閾値に触れていない。

## False positives・Unresolved

- 評価対象のedgeに false parent はない。
- 推論全体の unresolved/level_gap: summary は 6（範囲の先頭ページの親が範囲外のp18、組織の根）。detail は unresolved 2（070・080の根）と level_gap 74（すべて右側の備考欄の行。親の level と飛ぶ）。いずれもGT外で、親を確定扱いにしていない。
- **GT外のnode（未採点）**: detail 260 = 左側の目・子目（level 4–5）170 + 右側備考欄の「3桁+テキスト」行（level 6–14）89 + unplaced 1。総表 13 = 範囲内の他組織の行。これらの親は評価していない（精度の主張はGT内のedgeに限る）。

## Negative tests

p1555 の過年度表・罫線表は見出し候補にならず、要求186の親は項010（同一ページ）。合成テスト（項と要求の間に表行を挟む）で、先頭が3桁tokenの行は形だけなら候補になるが unplaced で、親にも子にもならない。親見出しが再掲されないページは前ページの親へ辿る（合成・実PDF）。テスト: 推論がGT・評価・凍結層をimportしない／GTのコード値・名称を埋め込まない／金額・符号の解釈を持たない／決定性（2回実行でartifactがバイト一致）。

## 感度診断（採点には使っていない）

事後の診断として、x係数を 0.05〜0.75、minClusterSupport を 2・3 に振った（既定は変更していない）。係数 0.05〜0.49 は両viewで結果が同一。0.5以上では総表の階段が1つに融合し、全て unresolved に縮退（false parentにはならない）。minSupport=3 では範囲内の組織が2つしかないため根の段が unplaced となり levelが1つずれ、detail の15エッジが unresolved。範囲に組織が1つだけの場合も同じで、実PDFのgoldenテストでも p1555–1602（組織070のみ）では再現した。

## Limitations

- **MHLW 1文書、1つの階層構造**。他省庁・他のsummary構造への一般化は未確認。評価対象は37ノード・35エッジで、100%でも母数は小さい。
- 開示した通り holdout は完全な未観察ではない（先頭の p20・p1603 は目視済み）。主な根拠は p1604–p1700。それでも階段の規則は development で観察した形（等間隔の階段+stack）の再適用で、holdout で新しい種類の構造に出会ったわけではない。
- GTは目次由来。研究GT（11ノード）は拡張GT（37ノード）の部分集合で、拡張分は同じ目次から転記した評価専用データ（この PoC で作成）。目次を読んで目次GTと比べているのではなく、**総表+明細見出し側から復元して目次GTで採点**しているが、GT自体の独立な検証（目次の転記ミスの確認）は research GT の11ノードとの整合のみ。
- view（summary/detail）と入力ページ範囲は与えた入力（走査範囲は目次の頁数から決めた）。ページ種別の自動判別・範囲の自動決定は検証していない。detail の「物理ページ=印字頁+8」は評価側のoffsetで、文書自身からのoffset復元は検証していない。
- level はxの階段の順位で、組織・項・要求の意味は付けていない。levelとGTの深さが一致したのは、この文書で階段が組織・項・要求の順に深くなっていたため（観測）。
- 見出し形状は「3桁+後続」「要求番号+NN-NN」に固定。MHLWの右側備考欄などの誤候補は node を増やす。下位層（LogicalRow）の誤りは未評価（今回のページでは必要情報が残っていた）。

## Stop-condition judgment

`GO`（MHLWの範囲）。research report §21.10 の「総表+明細見出しから目次GTの親エッジを pdf.js tokenだけで復元できた場合は main repo work を縮小版Aで続ける」を満たした。指示書の停止条件（下位3層に情報がない／body側から復元する根拠が不足／holdoutで一般化しない／GTを見ないとルールを決められない／コードlookupが必要／凍結層に戻らないと成立しない）はいずれも該当しなかった。ただし**他省庁への一般化は未確認**で、§21.10 の三つ目（他省庁に総表相当がない場合は階層をページ局所・文脈限定として記録し、MHLWに合わせて調整しない）の確認が次に残る。基準は結果を見て変えていない。

## Recommendation

1. 他省庁の総表相当・明細見出しで同じ観測（v1のまま、係数・規則の変更なし）を1〜2省庁で試し、一般化するか・どこで崩れるかを記録する。
2. 崩れた場合のみ v2 として規則を分けて記録する（v1の結果は残す）。
3. 総表の頁数列の候補（印字頁）から detail の見出しへ辿る対応づけ（総表↔明細の整合）は、今回は評価しておらず、次の候補。FieldResolver・最終SemanticRecordへは進まない。

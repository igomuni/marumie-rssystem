# 新リポジトリの構成案

状態: 構想。役割・公開・名前（`nihon-no-yosan`）・引き継ぐ規則は決定（6 節）、データの利用条件は未確認。推奨: 1 つのリポジトリの中を「core（純粋な関数と型）/ pipeline（データを作る）/ web（画面）」に分ける。大きなデータは git に入れず、版つきのデータセットとして配る。研究の経緯（GT・preregistration・PoC）は持ち込まず、いまのリポジトリに凍結して残す。

## 1. いまのリポジトリで重いもの・困っていること

| 項目 | 実測（2026-10-22） | 困ること |
|---|---|---|
| git の pack | 594 MiB | clone・worktree が重い |
| `tests/fixtures` | 157 MB、76 ディレクトリ | 本番の連鎖に要るのは 7 つ（約 116 MB）。残り 69 は研究の記録（GT・PoC・評価） |
| `public/data` | 169 MB（展開後）、80 ファイル | 画面ごとに V1・V2・UI 用が混在 |
| `scripts` | 49 本＋`pipeline-v2` 84 本 | 本番の連鎖と、研究・評価のスクリプトが同じ場所にある |
| MOF のデータ | 3 系統（V1・V2・原本の形の CSV） | どれが正か、画面ごとに違う |
| `docs/tasks` | 256 本＋archive 346 本 | 経緯を追うコストが高い |
| 層の規則 | `scripts` は `app/lib` を import しない | 行のキー（`mofRowKey`）や表記の揃え方（`ns`）を複製している |
| CI | `.github/workflows` なし | 検算・テストは手元で回すだけ |

本番の連鎖に要る fixtures: `budget-request-csv`、`budget-request-trend`、`budget-request-pdf-corpus`、`budget-request-jikou-youkyu`、`budget-request-mof`、`mof-archive-csv`、`mof-budget-request-match`。

## 2. 構成（推奨）

npm workspaces の monorepo にする。

```text
new-repo/
├─ packages/
│  ├─ core/        純粋な関数と型（React・Node の fs を使わない）
│  │               表記の揃え方（ns・fold・外字）、項・事項・目の鍵、行のキー、
│  │               名前でつなぐ処理（pairByName）、段階の定義、恒等式の検算
│  └─ pipeline/    データを作る CLI（Node）。core を使う
│     ├─ download/   原本の取得（URL と SHA-256 の固定）
│     ├─ extract/    原本 → 原本の形の CSV（概算要求 PDF、予算書の CSV・XML）
│     ├─ build/      CSV → 予算の一生の表・突合・年度推移
│     └─ publish/    画面用の JSON（gz）とデータセットの manifest
├─ apps/
│  └─ web/         Next.js。core を使う（pipeline は使わない）
├─ datasets/       データセットの manifest だけ（版・ファイル・SHA-256・作り方の commit）
├─ docs/
│  ├─ guides/      恒久的な仕様（いまの docs/*.md に当たる）
│  ├─ decisions/   決めたことを 1 件 1 ファイルで（ADR。短く）
│  └─ notes/       作業メモ（いまの task doc。古いものは消してよい扱い）
└─ tests/golden/   小さな検算用の fixture（数 MB 以内）
```

- **core を共有する。** いまの「scripts は app/lib を import しない」規則は、層を分けるためのもの。純粋な関数を `packages/core` に置けば、pipeline と web の両方から使えて、複製が要らなくなる。依存の向きは `web → core ← pipeline` で、web は pipeline を import しない。
- **pipeline は段に分ける。** download → extract → build → publish。段ごとに入出力を固定し、出力の SHA-256 を manifest に書く。いまの「再生成してバイト一致」の検算を、段ごとの決まりにする。
- **web は画面だけ。** いまの「Pages は状態管理・レイアウトのみ、ロジックは lib」の規則をそのまま持ち込む。

## 3. データの置き場

| 種類 | 大きさの目安 | 置き場 |
|---|---|---|
| 原本（PDF・zip・XML） | GB 級 | git に入れない。各自の `data/download/`。URL と SHA-256 だけ manifest に |
| 原本の形の CSV（概算要求・予算書） | 100 MB 級 | **版つきデータセット**として GitHub Releases に置く。manifest に SHA-256 |
| 予算の一生の表・突合・年度推移 | 数十 MB | 同上 |
| 画面用の JSON（gz） | 数 MB | git に入れる（いまの `public/data/v2/ui` は 5.6 MB） |
| 検算用の小さな fixture | 数 MB | git（`tests/golden`） |

- 年に 1 回の更新（8〜9 月の概算要求、1 月の予算書、秋の決算）ごとに、データセットの版を上げる（例: `request-2027.1`）。画面は、どの版から作ったかを manifest で示す。
- Releases の代わりに、rs-vis が使っている Supabase の Storage でもよい。ただし公開・非公開と費用の判断が要る。

## 4. 持ち込むもの・持ち込まないもの

| 持ち込む | 持ち込まない（いまのリポジトリに凍結） |
|---|---|
| core にする関数（表記の揃え方・鍵・突合・つなぐ処理） | 研究の記録（GT・preregistration・H1・PoC・評価の fixture 69 ディレクトリ） |
| 本番の連鎖: 突合 → 年度推移 → 事項要求 → 事項・目 → MOF の UI | V1 の MOF（`mof-kou-moku-*.json`）と V1 の生成スクリプト |
| 原本の形の CSV（データセットの初版として、いまの fixture をそのまま） | V2 の MOF（照合が要るときは、いまのリポジトリで回す） |
| /budget-request-trend、/budget-request-mof | /sankey-svg・/subcontracts・/quality など RS 中心の画面（いまのリポジトリと rs-vis で保守） |
| ガイド（docs/*.md のうち、持ち込む連鎖に関わるもの） | task doc（必要なものは decisions に要点だけ書き直す） |

- **概算要求 PDF の抽出（extract）は第 2 段で持ち込む。** 次に要るのは FY2028 の概算要求（2027 年 8〜9 月）なので、それまでに移せばよい。初版は、いまの CSV をデータセットとして取り込むだけにする。
- 持ち込んだ連鎖は、新リポジトリで再生成して、いまの出力とバイト一致することを最初の検算にする。
- **初版の再現性の境界:** 初版で保証するのは、凍結した CSV（データセットの初版）からの再生成まで。原本の PDF からの再抽出は、extract を移す次の段の対象。
- **基準データと最終的な正を分ける。** 原本の形の CSV は、正規化と構築の基準データ。最終的な正は公式の原本（PDF・zip・XML）で、CSV の値に疑いがあれば原本で確かめる。ガイドにもこの区別を書く。

## 5. 移行の順番

1. 空のリポジトリに、workspaces・tsconfig・lint・vitest・CI（GitHub Actions で tsc・lint・テスト）を置く。
2. `packages/core` に関数を移し、いまのテストも一緒に移す。
3. 原本の形の CSV を、データセットの初版として Releases に置く。`datasets/` に manifest。
4. build の連鎖を移し、いまの出力とバイト一致を確かめる。
5. `apps/web` に /budget-request-trend・/budget-request-mof を移す。
6. 予算の一生の表（構想の P0）を、新リポジトリで作る。
7. extract（PDF の抽出）を移す。FY2028 の概算要求より前。

/integrated-sankey は、予算の一生の表ができてから、新しいデータで作り直して移す（構想の P3）。

## 6. 決まったこと（2026-10-22）と、それによる変更

| 問い | 決定 | 構成への影響 |
|---|---|---|
| 役割 | 予算（概算要求〜決算）と RS をつなぐ。いずれ rs-vis に入れる可能性はあるが、そのときはコードを複製せず、このリポジトリを参考に指示書から作り直す | 下記 6.1・6.2 |
| 公開 | 公開 | 下記 6.3 |
| 名前 | `nihon-no-yosan`（一般名称） | 下記 6.4 |
| 規則 | ドキュメントの規則だけ引き継ぐ。それ以外（CLAUDE.md・スキル・作業の規則）は、最新の状況に合わせて作り直してよい | 下記 6.5 |

### 6.1 RS も範囲に入れる

- pipeline に RS の段を足す: download（RS の CSV 一括・シート）→ extract（原本の形の CSV）→ build（RS の事業・予算科目・支出）。
- **予算と RS のつなぎは core に置く。** RS の歳出予算科目は、予算書と同じ語彙（所管・組織／勘定・項・目の名前）を持つ。いまの突合と同じ鍵と表記の揃え方でつなぐ。年度の対応（RS の 1 回の提出に、前年度の執行・当年度の予算・翌年度の要求額が同居する）も core の定義にする。
- 大きさ: RS の原本（CSV 一括の zip）は 52 MB、シートは 9.9 MB。いまの RS の V2 の公開物は、提出年度ごとに 38〜42 MB。原本は git に入れず、V2 と同じく原本の形の CSV を版つきデータセットにする。
- 画面は、いまの /sankey-svg などを移すのではなく、予算の一生の表と RS の事業をつなぐ新しい画面として作る（構想の P3 の /integrated-sankey の作り直しがその中心）。

### 6.2 指示書で引き継げるようにする

rs-vis へはコードではなく指示書で渡す。そのため、**ガイドだけで作り直せること**を、ドキュメントの基準にする。

- ガイド（`docs/guides/`）に、データの契約（列・型・単位・鍵・空欄の意味）、つなぎ方の規則、検算（恒等式・件数・合計）、具体例（例: FY2024 消費者庁共通費を要求から決算まで）を書く。
- 検算は `tests/golden` の小さな fixture で再現できるようにし、ガイドから参照する。作り直した側も同じ値で確かめられる。
- 決めたこと（`docs/decisions/`）は理由つきで残す。作り直す側が、同じ判断をやり直さずに済む。

### 6.3 公開にする

- コードのライセンスは、いまと同じ MIT でよい（推奨）。
- **データの再配布の条件を、データセットを公開する前に確かめる**（未確認）。RS・財務省・各府省の利用規約と出典表記。原本（PDF・zip）は再配布せず、URL と SHA-256 だけ載せる。
- ドキュメントとコミットに、手元のパス・個人の作業ログを入れない。`docs/プロンプトログ*.ignore.md` のような作業ログは持ち込まない。
- データセットは GitHub Releases に置けば、Vercel のビルドからも認証なしで取れる。ただし、**利用条件を確かめるまでは公開しない**（公開前の関門）。それまでデータセットは手元か非公開の置き場に置く。

### 6.4 名前

`nihon-no-yosan`（日本の予算）に決定。候補だった `japan-budget-lifecycle` / `japan-budget-explorer` / `kuni-yosan` は使わない。

### 6.5 引き継ぐドキュメントの規則

いまの規則のうち、ドキュメントに関するもの:

- 恒久的な仕様はガイド、作業の記録はメモ（いまの `docs/*.md` と `docs/tasks/`）に分ける。コードとガイドからメモを参照しない（リンクが切れるため）。
- メモのファイル名は `YYYYMMDD_HHMM_タイトル.md`、タイトルの直後に 1〜2 行の要約（状態・結論）。索引のファイルは作らない（並行ブランチの衝突の元）。
- 長さは中身に合わせる。水増しの節・重複するまとめを書かない。
- コードフェンスに言語タグ（markdownlint MD040）。
- 事実はデータで裏を取り、取れないものは「未確認」「推測」と書く。

新しく足すもの: 決めたことの記録（`docs/decisions/`）と、指示書として通用するガイドの書き方（6.2）。

# cn 検証の houjin.db 非依存化と、支出先名寄せの cn 対応（設計）

作成: 2026-07-30 08:16 JST

## 背景

`cn`（法人番号による支出先の裏取り）が marumie にしか無く、rs-vis のデータには1件も入っていない。原因は生成経路が `data/houjin.db`（`.gitignore`・リポジトリ非管理）に直接依存していることで、DB を持たない環境ではパイプラインを回しても cn が付かない。

方針として **rs-vis でも cn ありにするのがあるべき姿**、かつ **今後サンキー図の支出先名寄せも cn 対応にしたい**という要件が出たので、両方を満たす形を設計する。

## 現状の整理

### cn には「検証」と「解決」の2種類がある

同じ houjin.db を使うが、成果物と使われ方が別。

| | 検証（cn status） | 解決（名寄せ） |
|---|---|---|
| 何をするか | 有効な法人番号 かつ houjin 公式名が支出先名と一致するか | 誤記載番号の統合（`mergeCn`）・欠落番号の補完（`supplement`） |
| 実装 | `scripts/score-project-quality.py` の `is_cn_verified()` — houjin.db に直接 SQL | `scripts/generate-recipient-resolution.py` → `recipient-resolution-{year}.json.gz` |
| 成果物 | **無し**（スクリプト内で消費し、`s='cn'` と `cnVerifiedCount` として結果だけ残る） | **ファイルとして残る**（2025: `mergeCn` 64件 + `supplement` 177件） |
| 消費者 | `project-quality-scores` / `project-quality-recipients` | `generate-recipient-index.ts`・`generate-sankey-svg-data.ts`（内訳集計のみ） |
| 他環境で再現できるか | **できない**（houjin.db 必須） | **できる**（`.gz` が Git 管理下） |

**この非対称が問題の本質。** 解決は成果物化されているのに、検証はされていない。

### 規模

2025年度の支出先 99,292行・ユニーク名 26,331件に対して:

- `s='cn'` で救済される行: **10,277行**（全体の約10%）
- 有効な法人番号のユニーク数: 19,017
- 名前の表記揺れ（NFKC＋法人格略記の統一で吸収できる分）: 166件のみ

**表記揺れは小さく、名寄せの主戦場は法人番号側。** 同名別法人の分離と、誤記載・欠落番号の解決が本体。

### サンキー図は cn 名寄せ未対応

`scripts/generate-sankey-svg-data.ts` の支出先集約キーは **生の支出先名そのまま**。

```ts
const recipientKey = spendingName;   // 正規化も cn も使っていない
```

`resolveRecipientKey()` は呼ばれているが、用途は「名前集約ノードが内包する法人番号の内訳（`corpAmounts`）」を作るためだけ。したがってサンキー図では:

- 表記揺れは別ノードになる（166件規模）
- **同名別法人が1ノードに混ざる**
- 誤記載・欠落番号の解決がノード分割に効かない

一方 `recipient-index`（`/api/recipients/[key]`）は `buildRecipientKey(name, cn)` で **cn 優先のキー**を使っており、**同じデータに対して2つの名寄せ規則が並立している**。

## 設計

### S1. cn 検証結果を成果物にする（houjin.db 非依存化）

`is_cn_verified()` の判定結果を `recipient-resolution-{year}.json` に追加する。houjin.db を持つ環境（marumie）で1回作れば、持たない環境（rs-vis・CI）でも同じ cn が再現できる。

```json
{
  "mergeCn": { "…": { "誤記載cn": "正規cn" } },
  "supplement": { "正規化名": "cn" },
  "verified": { "<cn>": ["<正規化名>", "…"] }
}
```

`verified` は「この法人番号で、この正規化名は houjin 公式名と一致する」という事実だけを持つ。houjin.db 全件（数百万行）を持ち出すのではなく、**RS データに出現した組み合わせだけ**に絞るので、2025年度なら1万件強・数百KB に収まる見込み。

- `score-project-quality.py` は houjin.db があれば従来どおり検証し、無ければ `verified` を参照する（フォールバック順を明記）
- 生成物に世代情報（houjin.db のスナップショット日付）を持たせ、鮮度を追えるようにする

**これにより「rs-vis でも cn ありにする」が構造的に成立する。** 現状の暫定対処（marumie が生成した `.gz` を rs-vis へコピー）も引き続き有効だが、S1 があれば rs-vis 単独でパイプラインを回せる。

### S2. 支出先キーの規則を1本化する

`app/lib/recipient-key.ts` の `resolveRecipientKey()` を**唯一の正典**とし、サンキー図・recipient-index・品質スコアが同じキーで集約する。

```text
優先順:
  1. 解決後の有効な法人番号（mergeCn・supplement 適用後）      → "cn:<13桁>"
  2. cn 検証済みの正規化名（verified で裏が取れているもの）    → "cn:<13桁>"（1に合流）
  3. 正規化名のみ（法人番号を持たない個人・外国法人・国の機関） → "name:<正規化名>"
```

サンキー図側の変更は `const recipientKey = spendingName;` を `resolveRecipientKey(...)` に差し替えることが中心だが、**ノードの分割単位が変わるためグラフの見た目と件数が変わる**。影響を測ってから入れる。

- 同名別法人が分離される（ノード数増）
- 表記揺れが統合される（ノード数減・166件規模）
- 支出先の TopN 順位が動く → `/sankey-svg` の URL 状態（`pr` ピン留め等）の互換に注意
- 表示名は「解決後キーの代表名」を決める必要がある（最大金額の名前を採る等）

`recipient-index` には既に `redirects`（旧キー → 現行キー）の仕組みがあるので、**同じ考え方をサンキー側にも使えるか**を検討する。

### S3. AI 判定への cn の伝え方を直す

現在 `_build_user_prompt()` は `辞書判定: {s}` として `cn` を渡すが、`JUDGE_SYSTEM` に辞書判定値の定義が一切無い。AI から見れば語彙外トークンである。

```python
# JUDGE_SYSTEM に追記する内容（案）
辞書判定の値: valid=辞書の正式名一致 / gov=国の機関 / supp=補助辞書一致 /
             cn=法人番号で公式名が一致（登記で実在確認済み）/
             invalid=辞書に無い / unknown=辞書未登録
```

あわせて `heuristic_judge()` に `cn` の分岐が無い（`unknown` 扱いに落ちて identify 1〜2 になる）ので追加する。

```python
elif status == 'valid' and has_cn:  identify = 3
+ elif status == 'cn':              identify = 3   # 登記で実在確認済み＝完全特定可
elif status in ('gov', 'supp'):     identify = 2
```

**プロンプト変更は次回再採点で初めて効く**ため、S3 は単独では意味を持たない。再採点とセットで入れる。

## 実施順

| 段 | 内容 | コスト | 前提 |
|---|---|---|---|
| 1 | marumie の `project-quality-recipients-{2024,2025}.json.gz` を rs-vis へ反映（コード＝`quality-recipients-loader` の型・`STATUS_META` の `cn` と**同時**） | 反映作業に同梱 | rs-vis 版 `/quality` は `STATUS_META[row.s]` を無ガード参照しており、**データだけ先に送ると実行時エラーで落ちる** |
| 2 | `heuristic_judge()` の `cn` 分岐追加 | 数行 | `fix/policy-eval-corrections` が同ファイルを触るので同時に |
| 3 | S1（cn 検証の成果物化） | 中 | `generate-recipient-resolution.py` の出力拡張＋`score-project-quality.py` のフォールバック |
| 4 | S3 のプロンプト定義追加 → 再採点（`score-project-quality.py` → `score-project-quality-ai.py`） | AI課金 | 既知不具合の列名7件修正（`generate-project-outcomes.py`）を先に当てて1回で回す |
| 5 | S2（支出先キーの1本化・サンキー図の cn 名寄せ） | 大 | 3 が前提。ノード分割が変わるため影響測定と URL 互換の検討が必要 |

1・2 は独立して着手できる。3 が入れば rs-vis 単独でパイプラインが回るようになり、4・5 の前提が整う。

## 決めていないこと

- **S2 の代表名の決め方**（最大金額の名前 / houjin 公式名 / 最新年度の名前）。houjin 公式名を採ると RS データに現れない名前が UI に出るため、利用者の検索語と食い違う懸念がある
- **`verified` の粒度**。`cn → 正規化名の配列` とするか `(cn, 正規化名) の組` とするか。前者は同一番号に複数の表記が紐づく場合に扱いやすい
- **houjin.db スナップショットの管理**。鮮度が cn の網羅率を左右するため、更新の運用（誰が・いつ・どう記録するか）を決める必要がある

## 実施記録 — AI評価済みデータの cn 付加（2026-07-30）

ブランチ `fix/restore-cn-in-quality-scores`。`project-quality-scores-2025.json.gz` を **AI 評価はそのままに cn 由来の項目だけ復元**した。再採点は行っていない（API 課金なし）。

### 手法

PR-1 で取り込んだ rs-vis 版と、その直前の marumie 版（`2f450b2^`・cn あり）を突き合わせたところ、**機械計算の土台が完全に一致**していた。

```text
rowCount / recipientCount / cnFilled / cnEmpty / spendTotal /
budgetAmount / blockCount / gapRatio   … いずれも 5,794 / 5,794 で一致
```

つまり両者は同じ CSV から作られており、差は cn 判定の有無だけ。そこで cn で値が変わる7項目を旧版から移植した。

```text
validCount / govAgencyCount / suppValidCount / invalidCount /
cnVerifiedCount / validRatio / axis1
```

### 結果

| 項目 | 更新件数 |
|---|---|
| `cnVerifiedCount` | 5,794（キーごと復活。合計 18,666） |
| `validRatio` / `axis1` | 各 1,498 |
| `invalidCount` | 106 |
| `validCount` / `govAgencyCount` / `suppValidCount` | 0（元から一致） |

`validRatio` 平均は 0.7662 → **0.7808** に戻った。

検証: cn 由来5項目が旧版と 5,794/5,794 一致、AI 由来10項目（`axisIdentify`・`axisPurpose`・`axisEffective`・`designClarity`・`evidenceReadiness`・`budgetProportionality`・`necessity`・`policyCategory`・`totalScore`・`aiSource`）が rs-vis 版と 5,794/5,794 一致。`tsc` クリーン、`vitest` 100件パス、dev で `/quality`・`/sankey-svg`・`/project-bubble` が 200、`/api/quality-scores` が 1,988事業に `cnVerifiedCount>0` を返すことを確認。

### 限界

`axisIdentify`（重み28）は AI が `辞書判定: unknown` を見て付けた値のままである。cn を AI 判定へ反映するには再採点が必要で、それは S3（プロンプトへの辞書判定値の定義追加）とセットで行う。**本作業は機械計算項目の整合を回復しただけ**で、AI 軸は cn 未反映のまま。

2024年度は marumie が独自版（cn あり）を保持しているため対象外。

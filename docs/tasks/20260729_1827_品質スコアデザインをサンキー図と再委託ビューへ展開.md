## 設計上の要点

### データ供給の形が2つある

- **marumie 方式**（#246 で分離）: ページ側が `useScoreDetailData(pid, year)` で `/api/quality-scores/recipients` と `/api/project-details/{pid}` を引き、`ScoreDetailDialog` へ props で渡す。ダイアログは表示に専念する
- **rs-vis 方式**: ダイアログ自身が内部で fetch し、`policy` だけを props で受ける

統合するなら marumie 方式に寄せるのが筋（`/subcontracts` も同じ hook を使っており、取得の重複を避けられる）。

### 政策評価は母集団依存で、単体では引けない

`PolicyEvaluation.overallPercentile` は全事業の分布から決まる。閾値（`AxisThresholds`）も母集団の分位点から算出される。したがって pid 単体の API では作れない。選択肢は3つ:

1. **`/api/policy-summary` を使う**（PR-1 で導入済み）— pid → `{o,d,e,t,x,n,r,a,c}` の圧縮形を全件返す。ただし `recommendationReason`・`findings`・`unusedTrend`・`spendDownRisk` は含まれず、rs-vis 版ダイアログの表示項目を満たせない
2. **`/api/policy-summary` を拡張**して判定理由まで返す — ペイロードが増える（全件×理由文字列）。pid 指定で1件だけ返すモードを足すのが現実的
3. **クライアントで `buildPolicyEvaluations` を回す** — `/quality` はこれ。ただし全件（5,794件・約9MB）のロードが前提で、サンキー図・再委託ビューに持ち込むには重い

**2（`/api/policy-summary` に pid 指定を足す）を推す。** 母集団の計算はサーバで一度だけ行い、必要な1件を全項目返す。`/quality` は従来どおり全件形を使えばよい。

### 共有コンポーネントの置き換え範囲

- `client/components/quality/ScoreDetailDialog.tsx` — rs-vis 版インライン実装で置き換え、`policy` を props に追加
- `client/components/quality/QualityScoreBlock.tsx` — サイドパネルの要約。推奨判断バッジを出すかは要判断
- 呼び出し側: `app/sankey-svg/page.tsx`（L4927 付近）、`app/subcontracts/[projectId]/page.tsx`（L991 付近）
- `/quality` はインライン定義を削り、共有コンポーネントの import に戻す

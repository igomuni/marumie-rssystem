# MOF予算データの階層JSONスキーマ案

現状は「事項」（`mof-jikou-{年度}.json`）・「目」（`mof-kou-moku-{年度}.json`）を別ファイル・
別生成スクリプトで持ち、`/mof-kou`だけが実行時に項単位へ突き合わせている。正準データが3つ
並立している状態を解消するため、**項を頂点に事項・目を子として持たせた1本の階層JSON**を
正準データにする案のスキーマとサンプル。

## ファイル構成案

| 現状 | 案 |
|---|---|
| `mof-jikou-{年度}.json` | 廃止（階層JSONから導出） |
| `mof-kou-moku-{年度}.json` | 廃止（階層JSONから導出） |
| （`/mof-kou`専用ファイルなし） | `mof-budget-{年度}.json`（新設・正準データ） |

RS紐づけ（`mof-rs-linkage-{予算年度}.json`・`mof-rs-kou-moku-linkage-{予算年度}.json`）は
**別系統のまま維持**する。MOF側の生成はRSデータに依存せず、RS側は独立した更新サイクル・
識別子引き継ぎロジックを持つため、混ぜると2つのパイプラインの関心が絡み合う。

## スキーマ

```ts
interface MOFBudgetData {
  metadata: {
    fiscalYear: number;
    eraLabel: string;
    accountTypes: MOFAccountType[]; // その年度に存在する会計区分
    budgetTypes: MOFBudgetType[]; // 当初・暫定・補正（第N号）・決算のうちその年度に存在するもの
    unit: 'yen';
    generatedAt: string;
    notes: string[];
  };
  sections: MOFSection[];
}

/** 項1件。事項・目は「項の子」であって「事項の子に目がある」わけではない（並列の内訳） */
interface MOFSection {
  /** 会計区分|予算種別|所管|組織/特会/機関|勘定|項コード */
  id: string;
  accountType: 'general' | 'special' | 'agency';
  budgetType: MOFBudgetType;
  ministry: string;
  organization: string;   // 一般会計のみ
  specialAccount: string; // 特別会計のみ
  subAccount: string;     // 特別会計・政府関係機関
  agency: string;         // 政府関係機関のみ
  sectionCode: string;
  sectionName: string;
  /** 目側の合計（事項側の合計とほぼ一致することを実測済み。不一致の4件は目名空欄行が原因） */
  amount: number;
  previousAmount: number | null;
  difference: number | null;
  jikou: MOFJikouLeaf[];
  koumoku: MOFKouMokuLeaf[];
}

interface MOFJikouLeaf {
  id: string;
  name: string;
  majorExpenseCode: string;
  majorExpenseName: string;
  amount: number;
  previousAmount: number | null;
  difference: number | null;
  /**
   * 説明（所掌事務・根拠法等。予算書の「説明」欄の全文）。既存の mof-jikou-{年度}.json に
   * 現在もある項目。長文で1事項あたり数百字になることがあるため、本体（sections配列）には
   * 入れず `mof-budget-descriptions-{年度}.json`（{leafId: string} のフラットな辞書）に
   * 分離する案。本体側は description を持たず、参照は id で行う
   */
  documentId: string;
  page: number | null;
  sourceUrl: string;
}

/**
 * 目1件。予算書は分類コードを `95016-2111-02` のように1本の複合コードで印字する
 * （特別会計は財政法の1桁が無く5分割: `95016-111-02`）。CSVでは6列に分解されており、
 * 現状は主要経費・使途別・目別の3つしか取り込んでいない。目的別・財政法公債金対象非対象別・
 * 経済性質別の3つは列としては存在するのに読み込んでいなかったため、この案で追加する。
 */
interface MOFKouMokuLeaf {
  id: string;
  subItemCode: string;
  subItemName: string;
  /** 複合コードの生値（予算書の印字と同じ表記。特別会計は財政法の桁が無い5分割表記） */
  classificationCode: string;
  majorExpenseCode: string;   // 主要経費別分類（2桁）
  majorExpenseName: string;
  objectiveCode: string;      // 目的別分類（3桁。docs/mof-budget-data-guide.md 4-3）
  objectiveName: string;
  fiscalLawCode: string;      // 財政法公債金対象非対象別分類（1桁・特別会計は無し。4-4）
  fiscalLawName: string;
  economicNatureCode: string; // 経済性質別分類（2桁。4-5）
  economicNatureName: string;
  purposeCode: string;        // 使途別分類（1桁。4-6）
  purposeName: string;
  amount: number;
  previousAmount: number | null;
  difference: number | null;
  /** 以下3つは決算のみ。予算の帳票では null */
  currentAmount: number | null;
  spent: number | null;
  carriedOver: number | null;
  unused: number | null;
  documentId: string;
  page: number | null;
  sourceUrl: string;
}
```

## 追加分の型定義（説明ファイル）

```ts
/** mof-budget-descriptions-{年度}.json。MOFJikouLeaf.id → 説明本文 */
```

## この設計で変わること

- `/mof-kou`: `sections`をそのまま一覧化。今の実行時結合（`mof-kou-loader.ts`の`buildYear`）が不要になる
- `/mof-jikou`: `sections.flatMap(s => s.jikou.map(j => ({...j, ...sの項情報})))`で導出（生成時に1回フラット化してファイル化するか、読み込み時に毎回フラット化するかは要検討）
- `/mof-kou-moku`: 同様に`koumoku`から導出
- 年度推移（identityKey方式）は変わらず使える。項の識別子は`accountType|organization/specialAccount/agency|subAccount|sectionCode`（予算種別・所管を除く）のまま

## 未決定事項（要相談）

1. **生成方式**: 事項別内訳（Web帳票）と科目別内訳（CSV）は別々にスクレイピング・パースする現行の2スクリプトを維持しつつ最後に統合するか、統合ロジックごと1本のスクリプトに書き直すか
2. **`/mof-jikou`・`/mof-kou-moku`用フラットビュー**: 生成時に別ファイルとして書き出す（現状に近い・ファイル数は変わらないが正準データは1つ）か、読み込み時にflattenするか
3. **`amount`の重複**: 項の`amount`（目側合計）は事項側の合計とほぼ同じなので、項オブジェクト直下に1つだけ持たせる設計で妥当か、事項合計・目合計を両方持たせて不一致を可視化するか
4. **説明（description）の分離粒度**: `mof-budget-descriptions-{年度}.json`を年度単位の1ファイルにするか（現状の事項数は最大2,685件/年度・全文で数百KB程度と推定）、それとも本体と同じ`/mof-kou`用途では不要なので生成自体をオプトインにするか

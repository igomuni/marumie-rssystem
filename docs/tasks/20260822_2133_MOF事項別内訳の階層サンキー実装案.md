# MOF 事項別内訳の階層サンキー 実装案

> **実装済み（2026-08-22）。**`/mof-hierarchy` として公開。設計からの変更点と、
> 実装中に見つかった不具合は末尾の「実装結果」を参照。

## 目的

**予算データを見る人が、国の予算がどの省庁のどの事業まで下りていくのかを、
1枚の図で上から下まで辿れるようにするため。**

現状 `/mof-jikou` は事項の一覧表で、絞り込みはできるが**流れが見えない**。
`/mof-budget-overview` は流れを描くが**会計区分までの粗い粒度**で止まっている。
両者の間、すなわち「所管 → 組織 → 項 → 事項」を追える図が無い。

## スコープ

`/mof-jikou` `/mof-budget-overview` とは**別の新規ページ**として作る。既存2ページは変えない。

- 列は左から **予算合計 → 所管 → 組織/特会 → 勘定/業務 → 項 → 事項** の6列
- 年度（2017〜2026）と予算種別（当初・暫定・補正・決算）を切り替える
- データ源は既存の `public/data/mof-jikou-{YEAR}.json`。**新しい生成物は作らない**

## 入力データの確認（令和8年度・当初予算で実測）

`MOFJikouItem` は必要な階層をすべて持っており、加工なしで6列に対応づく。

| 列 | フィールド | 令和8年度 当初の種類数 |
|---|---|---:|
| 所管 | `ministry` | 25 |
| 組織/特会 | `organization` / `specialAccount` / `agency` | 114 |
| 勘定/業務 | `subAccount` | 32 |
| 項 | `sectionCode` + `sectionName` | 1,104 |
| 事項 | `name` | 1,712 |

所管25・組織114・勘定32 に対して**項1,104・事項1,712**と、後ろ2列だけ桁が違う。

### 会計区分ごとにフィールドが入れ替わる

| 会計区分 | 所管 | 組織/特会 | 勘定/業務 |
|---|---|---|---|
| `general` | 省庁名 | `organization`（内閣本府 等） | なし（空） |
| `special` | **共管省庁を並べた文字列** | `specialAccount` | `subAccount`（勘定） |
| `agency` | 空 | `agency`（株式会社日本政策金融公庫 等） | `subAccount`（業務区分） |

- **所管が空になる会計区分がある**（政府関係機関）。所管列には会計区分名を置く
- **特会の所管名は極端に長い**。令和8年度は30文字超が1種
  （`国会、裁判所、会計検査院、内閣、内閣府、デジタル庁、防災庁、復興庁、…及び防衛省`）。
  そのまま出すとラベル欄を圧迫する
- **勘定を持たない特別会計が7つある**（交付税及び譲与税配付金・国債整理基金・国有林野事業債務管理・
  地震再保険・外国為替資金・東日本大震災復興・特許）。この列は**素通りさせる**必要がある

## 設計の決定（レビュー反映）

### 1. 根は単純合計にする。二重計上は許容する

一般会計122.31兆 ＋ 特別会計441.73兆 ＋ 政府関係機関4.72兆 ＝ 568.75兆。
うち127.62兆は会計間の繰入で二重に数えた分（`docs/mof-budget-data-guide.md` §6）。

**それでも根は1つの「予算合計」にする。**会計区分を選ばせると図が3つに割れ、
「どの省庁のどの事業まで下りるか」を1枚で追うという目的から外れる。
事項単位のノードを作ることを優先し、構成をシンプルに保つ。

**代わりに二重計上を画面に明示する。**見出しに単純合計であることと、
うち何兆円が会計間の繰入かを出す（`/api/sankey/mof-overview` が持つ `totals` と同じ値）。

政府関係機関は `ministry` が空なので、所管列には会計区分名（`政府関係機関`）を置く。

### 2. TopN ＋「その他」集約（`/sankey-svg` に倣う）

金額分布は 1兆円以上40件 / 1000億円以上159件 / **100億円未満1,221件（71%）**。

- 集約ノードは `/sankey-svg` の作法どおり `aggregated: true` を立て、灰色 `#999` で塗る
- 並び順も `sortPriority()` に倣い、集約ノードを列の末尾に置く
- TopN は列ごとに既定値を持ち、画面から変えられるようにする
- 対象は**項と事項**。所管25・組織114・勘定32 は集約しない

### 3. 値が無い列は素通りさせる。畳まない

- **勘定を持たない特別会計が7つある**（交付税及び譲与税配付金・国債整理基金・
  国有林野事業債務管理・地震再保険・外国為替資金・東日本大震災復興・特許）。
  一般会計も勘定を持たない。これらは勘定列に**ノードを作らず、帯を次の列へ通す**
- 1項＝1事項の行（平均1.6・**中央値1**・最大32）も列は畳まない。
  畳むと列の意味が行ごとに変わり「この列は何か」が読めなくなる

### 4. 収録されていないものは描かない（会計区分の特別扱いをしない）

予算種別によって収録されている会計区分が違う。

| 予算種別 | 一般会計 | 特別会計 | 政府関係機関 |
|---|---|---|---|
| 当初予算 | ○ | ○ | ○ |
| 暫定予算 | ○ | ○ | ○ |
| 補正予算 | ○ | ○ | 未対応（区分23） |
| **決算** | ○ | **帳票なし** | **帳票なし** |

決算の事項別内訳は一般会計（`77001`）にしかない。特別会計の決算（`78001`）は
勘定ごとの歳入歳出決算・財務諸表で事項レベルの帳票が無い（`docs/mof-budget-data-guide.md` §3）。
実測でも令和6年度の決算は `general` 1,446件のみ。

**採る案: 会計区分ごとの分岐を持たず、選んだ予算種別に収録されている事項だけで図を組む。**
無い会計区分の枝はそのまま現れない。決算だから一般会計に固定する、といった条件分岐は書かない。

根の値も「その予算種別に収録されている事項の合計」になる。何が収録されているかは
見出しに会計区分ごとの内訳として出す。

### 5. 補正予算の金額は改予算額

補正の `amount` は改予算額で、**号数をまたいで合算すると二重計上になる**
（`docs/mof-budget-data-guide.md` §3-1 制約1）。号数は択一で選ばせ、合算はしない。

補正の事項別内訳には**補正対象の事項しか載らない**ため、根の合計はその年度の
予算総額にはならない。図の見出しでその旨を明示する。

### 6. 選べる予算種別は年度で違う

```text
2017: 当初予算 / 補正予算（第1号） / 決算
2020: 当初予算 / 補正予算（第1号〜第3号） / 決算
2026: 当初予算 / 暫定予算 / 補正予算（第1号）
```

`metadata.budgetTypes` に実際に収録された種別が入っているので**選択肢はそこから作る**。
年度を変えたときに現在の種別が無ければ当初予算に落とす。

## レイヤ配置

CLAUDE.md の Layer Design Rules に従う。**新しい生成物は作らないので `scripts/` の変更は無い。**

| Layer | ファイル | 責務 |
|---|---|---|
| Domain Logic | `app/lib/mof-hierarchy-sankey.ts`（新規） | `MOFJikouItem[]` から6列のノード・リンクを組む。TopN集約もここ。Pure |
| Domain Logic | `app/lib/mof-sankey-layout.ts`（既存） | 座標計算。列の決め方を「最長経路」から「指定列」に切り替えられるようにする |
| API Layer | `app/api/mof-hierarchy/route.ts`（新規） | `year` / `budgetType` / `accountType` / TopN を受け、ロジックは `app/lib/` に委譲 |
| API Layer | `app/lib/api/mof-jikou-loader.ts`（既存） | 読み込みはこれを再利用 |
| UI | `client/components/mof-hierarchy/`（新規） | 図・コントロール。API を直接叩かない |
| Page | `app/mof-hierarchy/page.tsx`（新規） | 状態管理・API呼び出し・レイアウトのみ |
| Types | `types/mof-hierarchy.ts`（新規） | ノード種別と API レスポンス |

### 既存資産の再利用

- **配置計算**: `app/lib/mof-sankey-layout.ts`。ただし現状は列を最長経路で決めている。
  今回は階層が固定なので**列番号を外から与える**経路を足す（既存の呼び出しは変えない）
- **描画**: `client/components/mof-budget/SankeyChart.tsx`。ラベルの衝突回避と
  ホバーは共通で使えるが、`MOFBudgetNodeDetails` に結合している。
  ノード詳細の型をジェネリックにするか、描画部分を切り出して共有する
- **配色**: `app/lib/mof-sankey-constants.ts` の5色。列ごとに色を割り当てる
- **年度セレクト**: `components/navigation/YearSelect`
- **ビュー切替**: `client/components/mof-budget/ViewSelect.tsx` の作法（セレクトを右上に並べる）

## データの流れ

```text
public/data/mof-jikou-{YEAR}.json（既存・.gz のみ Git 管理）
  ↓ app/lib/api/mof-jikou-loader.ts（既存）
  ↓ app/lib/mof-hierarchy-sankey.ts（新規。会計区分・予算種別で絞り、6列に畳んでTopN集約）
  ↓ app/api/mof-hierarchy/route.ts（新規）
  ↓ app/mof-hierarchy/page.tsx
```

ノードIDは階層のパスから作る（`ministry|organization|subAccount|sectionCode|name` の前方一致部分）。
事項に公式なIDが無いのは `docs/mof-budget-data-guide.md` §3-1-1 のとおりで、
**同名の事項が複数の項に存在する**ため、名前だけでノードIDを作ると別物が合流する。

## 検証

生成物を作らないので `validate-*` は増やさない。代わりに **API 応答の自己整合**を確認する。

- 各列のノード値の合計が根の値に一致すること（集約後も落ちが無いこと）
- リンクの流入と流出が各ノードで一致すること
- 会計区分 × 予算種別の全組み合わせで、根の値が `/api/mof-jikou` の
  `summary.byAccountType` と一致すること

これらは `app/lib/mof-hierarchy-sankey.ts` の単体テストとして書ける
（`app/lib/` に `.test.ts` を置く既存の作法がある: `sankey-query.test.ts` 等）。

## 決めていないこと

- ノードを選択したときの挙動（絞り込み・詳細パネル）。まず図が出ることを優先する
- `/mof-jikou` の一覧表との相互リンク
- 特別会計の決算を科目別内訳 CSV から補うかどうか（新しい生成物が要る）
- 政府関係機関の補正（区分23）の取り込み（`docs/mof-budget-data-guide.md` §3-1 制約1）

### 構成

| 層 | ファイル |
|---|---|
| Domain | `app/lib/mof-hierarchy-sankey.ts`（6列への畳み込みと集約）＋ `.test.ts` |
| Domain | `app/lib/mof-hierarchy-focus.ts`（選択した筋の抽出と金額の付け替え）＋ `.test.ts` |
| Domain | `app/lib/mof-sankey-layout.ts`（配置計算。既存を型引数化して共用）＋ `.test.ts` |
| Domain | `app/lib/mof-hierarchy-constants.ts`（配色・レイアウト定数） |
| API | `app/api/mof-hierarchy/route.ts` |
| UI | `client/components/mof-hierarchy/`（HierarchyChart / HierarchyControls / HierarchySearch） |
| Page | `app/mof-hierarchy/page.tsx` |
| Types | `types/mof-hierarchy.ts` |

生成物は増やしていない（`mof-jikou-{YEAR}.json` を読む）。

### 設計から変えた点

**列ごとのノード数上限を足した。**親ごとの TopN だけでは列の総数を抑えられない。
組織114 × 項の TopN のように掛け算で増え、実測で項730・事項1,184になり
1ノードが1px未満になった。列単位の上限（既定40）を併せて掛ける。

**「その他」を列ごとに1つにした。**当初は親ごとに作っていたが、灰色の細い行が
延々と並び `/sankey-svg` のような1本の太い集約ノードにならなかった。
集約どうしを繋いで流れを保ち、名前に件数を出す（`その他 1,672件`）。

**素通りの列に透明な通過ノードを置いた。**何も置かないと帯がその列の実ノードを
横切って重なる。場所だけ確保し、描画・ラベル間隔・列合計・TopN・集約の件数からは除く。

**会計区分の選択は入れなかった。**根を単純合計にする判断（レビュー済み）に従い、
二重計上は注記で示す。

### 実装中に見つけた不具合

**1. ラベルスロットが固定 px なので縮尺が決まらない。**
「合計 ÷ 使える高さ」で割ると、小さいノードがスロットまで膨らんだ分だけ列が
指定より高くなる。ズームを下げて誤魔化していたため下に大きな空白が残っていた。
スロットに達するノードを固定分として除きながら数回繰り返して収束させる計算に変えた。

**2. 絞り込みで列の合計が根を超える。**
集約ノードの値は流入から再計算していたが、そこから次の列の集約へ出るリンクは
全量のままだった。集約は列をまたいで連鎖するため下流ほど膨らみ、
実測で事項列180.44兆 > 根145.60兆になった。下流リンクも同じ割合で縮める。

**3. 選択したまま年度を変えると空の図になる。**
存在しないノードIDが残ると関連が自分1つだけになる。ノードが消えていたら解除する。

**4. `pushState` を state 更新関数の中で呼び、履歴が二重に積まれた。**
React が更新関数を2回評価する場面（StrictMode）で1回の「戻る」では戻らなくなる。
副作用は更新関数の外に出した。

**5. 絞り込みが元のリンク配列を破壊していた。**
`link.value *= ratio` で入力の配列要素を直接書き換えていた。切り出してテストを
書いたときに気づいた。コピーしてから扱う。

### `/sankey-svg` から取り入れた作法

- ラベルはノード自体をずらして1行分の場所を確保する（`MAP_LABEL_SLOT_PX` 相当）。
  ラベルだけをずらすと箱から離れて引き出し線だらけになる
- 横は画面固定・縦だけ縮尺を変えるズーム（文字が伸びない）
- 列見出しの下に列の合計を出す
- 集約ノードは灰色・列の末尾・手前に区切りの余白
- 配色は `sankey-svg-constants.ts` と同じ5色

- 政府関係機関の補正（区分23）

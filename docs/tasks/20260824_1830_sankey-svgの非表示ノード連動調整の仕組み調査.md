# /sankey-svg の非表示ノード連動調整の仕組み調査

## 目的

mof-hierarchyのオフセット対応（[20260824_1207](20260824_1207_mof-hierarchyオフセットの窓手前ノードをsankey-svgに完全一致させる設計案.md)）で「事項」以外の対象がうまく動いていないように見えるとの指摘を受け、対応の前段として `/sankey-svg`（`app/lib/sankey-svg-filter.ts`）が「あるノードを隠したとき、関連ノードをどう連動させているか」を実測した。コード変更はしていない、調査のみ。

## 結論（要約）

`/sankey-svg` は単純な「隠した分を祖先から引く」一方向カスケードではない。**3つの独立した仕組み**が組み合わさっている。

1. **金額の調整（双方向・非対称）**: 支出先を隠すと上流（事業）の表示値を縮める。事業を隠すと下流（支出先）の表示値も縮む。ただし縮め方の**計算式は方向ごとに別物**で、共通の「祖先へ引き算」のような単一ルールでは実装されていない
2. **順位そのものの動的な入れ替え**: 事業のTopN選抜は、予算額の固定順位ではなく「現在窓に入っている支出先からの流入額」で**毎回再計算**される。支出先側のオフセットを動かすと、TopNに入る事業の顔ぶれ自体が変わりうる
3. **真の値の併記**: 縮めた値と元の値の両方を保持し（`rawValue`/`isScaled`）、ラベルに両方出す。個々の帯（エッジ）は縮めず真の値のまま流すので、箱の中で帯が余る／欠ける見た目のズレが意図的に残る

## 1. 金額の調整

### 支出先→事業（`projectAdjustedBudget`、sankey-svg-filter.ts:246-259）

```ts
const sv = n.value - (projectAboveWindowSpending.get(n.id) || 0); // 窓の手前を除いた支出額
const fraction = Math.max(0, Math.min(1, sv / n.value)); // 可視割合
projectAdjustedBudget.set(budgetId, budgetNode.value * fraction); // 予算額 × 可視割合
```

事業の「予算」ノードの表示値は、真の予算額に「支出額のうち窓に入っている割合」を掛けて縮める。窓の手前（オフセットで飛ばした支出先）への支出だけを分子から除く。**末尾（集約に回った支出先）への支出は可視割合に含まれる**——集約ノードとして残っているので「見えている」扱い。

この `projectAdjustedBudget` は `total→所管`（`ministryBudgetValue` 経由、478-491行目）・`所管→事業`（645行目）・`事業(予算)→事業(支出)`（676行目）の3か所のエッジ値に使われ、根まで伝播する（[20260824_1207](20260824_1207_mof-hierarchyオフセットの窓手前ノードをsankey-svgに完全一致させる設計案.md) で実機検証済み）。

### 事業→支出先（`recipientWindowValue`、215-222行目・591-597行目）

```ts
for (const e of allEdges) {
  if (windowRecipientIds.has(e.target)) {
    projectWindowValue.set(e.source, ...);
    if (!projectOffsetMode || !aboveWindowSpendingIds.has(e.source)) {
      recipientWindowValue.set(e.target, (recipientWindowValue.get(e.target) || 0) + e.value);
    }
  }
}
...
const val = recipientWindowValue.get(rid) || 0; // 支出先ノードの表示値
```

支出先の表示値は「**現在TopNの窓に入っている事業からの流入だけを足した額**」。事業側のオフセット（`projectOffsetMode`）が効いているときは、窓から外れた事業（`aboveWindowSpendingIds`）からの流入をそもそも合算しない。つまり事業を隠すと、その事業から支出を受けていた支出先の表示額も連動して縮む。

**方向による非対称**: 支出先→事業は「fraction（割合）で予算額を縮める」という掛け算方式。事業→支出先は「窓に入っている分だけ愚直に合算する」という足し算方式。同じ考え方の使い回しではなく、それぞれの列の性質（事業側は"予算額"という別建ての値を持つが、支出先側は流入の合計そのものが値）に合わせて別々に実装されている。

## 2. TopN選抜の動的な再ランキング

**最大の発見**: 事業のTopN選抜は固定順位ではない。

```ts
// sankey-svg-filter.ts:261-284
topMinistryAllProjects.sort((a, b) => {
  // 通常は「窓+集約に入っている支出額」で決める。予算額の大小ではない
  const va = (projectWindowValue.get(a.id) || 0) + (showAggRecipient ? (projectTailValue.get(a.id) || 0) : 0);
  const vb = (projectWindowValue.get(b.id) || 0) + (showAggRecipient ? (projectTailValue.get(b.id) || 0) : 0);
  if (vb !== va) return vb - va;
  // 同値時のみ予算額でタイブレーク
  ...
});
const topProjectNodes = topMinistryAllProjects
  .filter(n => 可視流入がある || pinned || includeZeroSpending)
  .slice(0, topProject);
```

支出先オフセットを動かして「窓」に入る支出先の顔ぶれが変わると、各事業の「窓+集約への流入額」も変わり、**事業の順位そのものが入れ替わる**。ある回では表示されていた事業が、支出先オフセットを進めた次の回では別の事業に取って代わられて消えることがある（予算額は変わっていなくても）。

これは mof-hierarchy には無い仕組み。mof-hierarchy の各列のランキングは常にノード自身の真の金額（`rawAmount`相当）で固定されており、下流の窓の状態によって上流の順位が動くことは無い。/sankey-svg のこの挙動を再現するなら、「項のランキングを、現在の事項オフセット窓に入っている事項の合計額で毎回再計算する」といった作り込みが要る——これは今回の対応の範囲を大きく超える。

**所管（ministry）はこの再ランキングの対象外**（8-33行目、`getTopMinistriesInScope`）。所管のTopN選抜は常に所管の真の予算額（固定値）でソートする。「事業だけが動的再ランキングされ、所管はされない」という非対称も存在する。

## 3. 真の値の併記とエッジの非調整

```ts
// project-budget ノード（254-258行目で算出した adjustedBudget を使う箇所、3495行目）
{node.name} ({formatYen(node.value)}){node.isScaled && node.rawValue != null && (
  <tspan fill="#777"> / {formatYen(node.rawValue)}</tspan>
)}
```

縮めた表示値（`value`）と元の真の値（`rawValue`）を両方保持し、ラベルに両方出す。列見出しの合計（`colAmounts`）は事業列だけ `rawValue` を使う（3511-3512行目）——**個々のノードの箱は縮んでいても、列全体の見出し合計は真の値のまま**、という使い分けがある。

エッジ自体（`project-spending → window recipients`、685-687行目）は `allEdges` の真の値をそのまま使い、縮めない。結果として、縮めた事業の箱の中で、そこから伸びる帯の合計が箱の高さに届かない（余る）見た目のズレが生じるが、これは意図的に許容されている（コメントなし＝暗黙の設計判断だが、`rawValue` の併記と合わせて考えると「この箱は本来もっと大きいが、見えている範囲だけを表示している」という手がかりとして機能している）。

## 次の一歩（実装はまだ着手しない）

ユーザーの「他の対象（組織・勘定・項・所管）がうまくいっていなさそう」という指摘の原因は、上表の「上流ノードの動的再ランキング」の**不在**である可能性が高い——/sankey-svg では事項だけでなく、実質すべての中間列（事業＝mof-hierarchyでいう項〜組織相当）も、真の金額ではなく「現在の窓の可視額」で並び替わる。mof-hierarchy は葉（事項）だけを /sankey-svg 流に倣ったが、中間列は元の「固定順位」設計のまま据え置いた。この差分が「事項は良いが他はおかしい」という体感の正体である可能性がある。次回、具体的な repro（どの対象で・どう操作すると・何が期待と違うか）を確認してから対応方針を決める。

## 追記: 項のTopN選抜を事項の可視額で再ランキングする実装（同日）

具体repro：「事項オフセットを進めても項の集約ノードの数が変化していない」。実測すると、
項自身のTopN/オフセットは事項オフセットとは独立して固定順位のままで、/sankey-svg の
「事業のTopNが下流の可視額で毎回入れ替わる」仕組みが無いことが直接の原因と確認できた。

ユーザーの意向（「/sankey-svgと同じにしたい」大規模変更を選択）を受け、`app/lib/mof-hierarchy-sankey.ts`
の残すノードを決めるループの処理順序を **`ministry → organization → subAccount → item → section`**
に変更した（木を辿る順序=`HIERARCHY_COLUMNS_EXCEPT_TOTAL` とは別に、ランキング決定専用の順序を用意）。
事項を項より先に決めておくと、事項の窓の手前で隠した分を祖先（項含む）から引く既存の減算処理が
自然に効き、その後に決める項のランキングが「真の合計」ではなく「事項オフセットで見えている額」を
使うことになる——専用の再ランキング式を別途実装せずに済んだ。組織・勘定・所管は今までどおり
事項より前の処理のままなので、この再ランキングの影響を受けない（/sankey-svg の所管と同じ）。

副作用として2点対応した：
- 項が項自身の窓の手前で隠れても、配下の事項が既に個別に kept（事項が先に決まっているため）なら
  隠さない（子孫への再帰的な hidden マーキングに「既に kept ならスキップ」のガードを追加）
- 帯の起点解決（`resolveSource`）が、hidden な祖先（集約が存在しない）を飛び越えてさらに上の
  祖先まで遡るよう拡張。項自身が手前で隠れても、その配下の kept な事項の帯が迷子にならない

実測（本番データ）で確認：`1,066項` という**件数の数字自体**は事項オフセットだけでは変わらない
（項自身のTopN=40が動かない限り、全項数からTopNを引いた値は構造的に一定のため）。変わるのは
集約の**中身**（`aggregatedTop`）——事項オフセットを進めると、集約に入っている項の顔ぶれが
完全に入れ替わることを確認した。ユーザーの「集約ノードの数」という表現は、この中身の変化を
指していたと判断し、そちらで解決とした。

## 追記2: 配下の事項が全件隠れた項を項自身も隠す（同日）

「事項オフセットで配下の事項が非表示になった項ノードを非表示にする必要がある」との指摘。
確認したところ、**項は必ず1件以上の事項を持つ**（事項ゼロの項は `buildFullNodeMap` の
仕組み上作られない。実データでも1,106件全項について直接つながる事項が1件以上あることを確認済み）。
つまり「項の配下の事項が全件隠れる」＝「その項には表示すべき中身が無くなる」状態であり、
放置すると0円の項が kept として残ったり、中身のない状態で集約にカウントされたりする。

`/sankey-svg` の `topProjectNodes` フィルタ（可視流入ゼロの事業候補からそもそも除く、
sankey-svg-filter.ts:286-290 相当）と同じ考え方で、事項の列（`item`）を処理した直後に、
配下の事項が全件 `hidden` になった項を検出し、項自身も `hidden` に追加する処理を足した
（祖先への金額の再減算は既に0のため実質no-op、二重減算にならないよう「既に hidden な項は
スキップ」のガードも入れた——組織レベルなど、より上流の列で先に隠された項と処理が重ならないため）。

実測（本番データ、`offsetItem=1600&topItem=100`）で確認：`columnCounts.section` が
854→88 に大きく減る（配下の事項が全件窓の外に出た項が数百件規模で発生し、いずれも
項として除外されることを確認）。

ユニットテスト3本を追加（2本が旧実装に対して赤であることを確認してから実装）。

## 追記3: 項オフセットで明示的に隠れた項の配下は道連れで隠す（同日）

「オフセット対象を項にしたときに、項が非表示の事項が残っている」との指摘。原因は
追記2で入れたガード（`if (kept.has(id)) continue`）——事項は項より先に処理されるため、
項自身のTopN・オフセットが無ければ配下の事項は先に kept になる。項オフセットで
その項自身が明示的に窓の手前へ隠れても、このガードのせいで既に kept な事項は
そのまま生き残ってしまっていた。

このガードは元々「項がTopN選抜で単に集約（tail）に回っただけ」のケース向けに
書いたつもりだったが、実際にそのケースは別経路（`others` ループの非再帰処理）で
処理されており、このガードが効くのは「項自身が明示的に hidden になった」場合
**だけ**だった。ユーザーの意図（項オフセットで押し出したら中身ごと消えてほしい）
と噛み合わなかったため、ガードを撤回し、明示的に hidden になった項の配下は
kept 状態に関わらず道連れで隠すよう変更（`kept.delete(id)` も追加）。

項のTopN選抜が可視額で再ランキングされて tail（集約）に回っただけのケースは
このコードパスを通らないため、事項が集約ノードから個別に顔を出す挙動
（追記1で実装したもの）には影響しない——実際、既存の関連テストは変更無しで
green のまま。

ユニットテスト2本を追加。旧実装に対して赤であることを確認してから実装した。

## 追記4: 項の道連れで欠けた事項の窓を次点で埋め戻す（同日）

「項で非表示になった関連の事項の分だけ、事項の集約から表示されるノードを補填する
ようにしてください」との指摘。追記3の対応（項が明示的に隠れたら配下の事項も
道連れで隠す）を入れた結果、事項の表示件数が設定したTopN（既定40）より少なく
なることがある——道連れで欠けた分の埋め戻しをしていなかったため。

実装: 事項列を処理する際の候補一覧（金額順、`itemRankable`）とTopNの上限
（`itemLimit`）をループの外側に保持しておき、全列の処理が終わったあと
（項オフセットによる道連れ hidden 化も含めて確定したあと）に、
`kept` の事項件数が `itemLimit` に満たなければ、`itemRankable` を順に
辿って次点（集約に回っていた事項）を `kept` に繰り上げる。

実測（本番データ、既定TopN=40で `offsetSection=1&topSection=5`）で確認：
道連れが発生する設定でも事項の表示件数は常に40のまま。

ユニットテスト2本を追加。旧実装に対して赤であることを確認してから実装した。

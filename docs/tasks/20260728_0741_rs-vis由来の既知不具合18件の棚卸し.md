# rs-vis 由来の既知不具合18件の棚卸し（修正は別タスク）

作成: 2026-07-28 07:41 JST / 更新: 2026-07-28 08:15 JST
状態: **両リポジトリとも未修正**。修正は marumie のブランチ `fix/policy-eval-corrections` に退避済みで、適用は別タスク。

rs-vis から逆流取り込みしたコードに元からあった不具合18件（CodeRabbit の指摘12件＋自己点検で追加発見した列名6件）。

一度は marumie の PR #291 で直したが、**rs-vis はそのままの形を維持して取り込む**方針に切り替えたため、修正コミットを PR から外して別ブランチへ退避した。結果として marumie・rs-vis の双方に同じ不具合が残っている。ここには対象と根拠を残し、別タスクで両方へ当てられるようにする。

## 前提

- 修正の実体: marumie ブランチ `fix/policy-eval-corrections`（`caf79c7` + `a7da14b`）— 14ファイル
- 適用先は2つ: marumie `main`（PR #291 マージ後）と rs-vis `main`（`1f69d0a` 以降）
- rs-vis は marumie にリモート `rsvis` として登録済み。14ファイル中 **13ファイルは rs-vis にも存在し、すべて修正前の状態**（残る `types/policy-evaluation.ts` は本対応で新設）
- 確認方法: `git show rsvis/main:<path>` の中身を修正前の文字列と照合（全件で一致を確認済み）

## 公開サイトに影響が出ているもの

### 1. `percentileRank` の同点バグ（app/lib/policy-evaluation.ts）

下限位置をそのまま順位に使っており、同点の塊が丸ごと最下位の帯に落ちる。AI採点は 0-10 を 0-100 に伸ばした離散値のため同点が大量に出る。

rs-vis で `buildPolicyEvaluations` を呼ぶ箇所は3つ（`app/quality/page.tsx`・`app/api/policy-summary/route.ts`・`app/lib/project-map.ts`）で、**公開サイトの推奨判断が実際にずれている**。marumie で midrank に直した際の変化:

```text
継続          2,127 → 2,245
要改善        1,522 → 1,515
条件付き継続   1,363 → 1,252
縮小            444 →   444
再設計          307 →   307
終了・廃止候補    31 →    31
```

最下位帯（終了・廃止候補）は 31件で不変。設計コメントが想定していた「5%で31件」の水準は保たれる。

**データ再生成は不要**。パーセンタイルは実行時に母集団から計算するため、`project-quality-scores-*.json.gz` は変わらない。コードだけ直せば出力が正しくなる。

### 2. 列名7件の不一致（scripts/generate-project-outcomes.py）

**当初 `effectAssessment` 1件と見たが、全列名を突き合わせた結果 7件だった。** 原因も「書き間違い」ではなく、**配布ZIPのヘッダと展開済みCSVのヘッダが別物**であることによる。

ZIP展開時に全角記号が正規化されている（2024・2025 の両方で同一の変換を確認）:

```text
－ (U+FF0D 全角ハイフン)  →  ー (U+30FC 長音)     ※本来 - であるべきところの誤変換
／ (U+FF0F)              →  / (U+002F)
（ ）(U+FF08/FF09)        →  ( ) (ASCII)
```

スクリプトの列名は配布ZIPのヘッダを書き写したもので、実際に読む `data/year_{YEAR}/` の展開済みCSVとは一致しない。不一致だった7列:

| 対象 | 影響を受けるフィールド |
|---|---|
| 4-1 | `effectAssessment`（`－`）、`reflection`・`reflectionDetail`（`／`） |
| 3-2 | 派生元・派生先の `種別`（`（）`）、派生元・派生先の `活動目標／成果目標`（`／`・余分な空白） |

現行の `rs2025-project-outcomes.json.gz` はこれら7フィールドすべてに値が入っている（`effectAssessment` 3,095件、`reflection` 5,034件、`logicModel.links` 5,758件で `fromKind`/`toKind` も充足）。つまり**コミットされているスクリプトはデータを生成した版に対する後退**であり、**このまま回すと7フィールドが黙って空になる**。

修正後は 2024・2025 の両年度で全列名が解決することを確認済み。あわせて、引けなかった列名をファイルごとに一度警告する `make_col()` を導入した（同種の後退を次から即座に検知するため）。

### 3. CSV数式インジェクション（scripts/export-luna-scores.ts・export-policy-decision-template.ts）

`=` `+` `-` `@` 始まりのセルを表計算ソフトが数式として実行する。引用符では防げない。生成物は `data/exports/` に commit されており、rs-vis はパブリックリポジトリのため、開いた人の環境で発火し得る。

## 発動時の手順

修正は marumie のブランチに退避してある。marumie・rs-vis のどちらにも同じコミットを当てられる。

```bash
# marumie へ当てる場合
git checkout -b fix/policy-eval-corrections-apply main
git cherry-pick caf79c7 a7da14b

# rs-vis へ当てる場合
cd /Users/igomuni/MyGitHub/rs-vis
git remote add marumie-local /Users/igomuni/MyGitHub/marumie-rssystem   # 未登録なら
git fetch marumie-local
git checkout -b fix/policy-evaluation-corrections
git cherry-pick marumie-local/fix/policy-eval-corrections~1 marumie-local/fix/policy-eval-corrections
```

注意点:

- **`types/policy-evaluation.ts`（新設）が一緒に入る必要がある**。`app/lib/policy-evaluation.ts` は共有型をこのファイルへ移し、再エクスポートする形に変えてあるため、片方だけでは型解決に失敗する
- `.claude/commands/data-update.md` の変更も含まれる。rs-vis 側にも同ファイルがあるので衝突しない
- `a7da14b` には本ドキュメント自身の追加も含まれる。rs-vis へは `docs/tasks/` を展開しない運用なので、rs-vis 側では除外する
- rs-vis の `origin` は `team-mirai-volunteer/rs-vis`。PR を出す前にユーザー確認を取ること


## 別タスクにした理由と、待たない方がよい線引き

rs-vis はそのままの形を維持して取り込む方針とした。取り込みと修正を1つの PR に混ぜると、どこまでが rs-vis の原型でどこからが marumie の判断かが差分から読めなくなるため、分離自体は妥当。

ただし **1（percentile）と 3（CSV数式）は公開済みの成果物が実際に誤っている／危険な状態**である。特に 1 は marumie で `/project-bubble` を公開した時点で marumie 側にも同じずれが出る（推奨判断が数百件動く）。rs-vis 側で `generate-project-outcomes.py` を回す予定が立てば 2 も待てなくなる。この3件のどれかが動き出したら、他の作業の完了を待たず先に当てること。

# 統合サンキー作り直し：/sankey-svg 引き継ぎ範囲の洗い出し

## 前提

これまでの `/integrated-sankey`（Codex実装 → Claudeの累積修正）は作り直す。
新方針は次の3点。

1. `/sankey-svg` の「サンキー図そのもの以外」のコントロール一式をそのまま引き継ぐ
2. ノードは**MOF項・RS事業の2種類のみ**（省庁列・支出先列は無い）
3. **目エッジは持たない**。項と事業を直接結ぶ（目は事業詳細パネルの内訳としてのみ残る）

本書は `app/sankey-svg/page.tsx` の state・UI領域を一通り洗い出し、上記方針の下で
「そのまま引き継ぐ」「作り替えて引き継ぐ」「不要」を判定したもの。実装計画ではない。

## 最重要の発見：検索とフィルタは別物

これまでの実装が的を外していた根本原因はここにある。

`/sankey-svg` の**検索**（左上・入力＋`.*`トグル）は、**グラフを絞り込まない**。
入力に一致するノードをドロップダウンに列挙し、クリックすると該当ノードへパン/ズームして
選択するだけの「ジャンプ機能」（`handleSearchSelect` → `focusOnNeighborhood`）。

グラフの表示自体を絞り込むのは、検索ボックスに内包される**別パネルの「フィルタ」**
（会計区分・省庁・予算/支出レンジ・政策評価スコア・再委託等）であり、
これは `filterExcludedIds` を通じて描画対象から実際にノードを除外する。

前回までの実装は、この2つを1つの「検索ボックス」に統合し、常にグラフ側を絞り込む
動作にしていた。作り直す際は**検索＝ジャンプ、フィルタ＝絞り込み、の分離を再現する**。

## 引き継ぐ（そのまま／ほぼそのまま）

サンキー図の描画ロジック以外で、2ノード種別・目エッジ無しの制約と無関係に成立するもの。

## 作り替えて引き継ぐ（概念は使うが中身が変わる）

| 領域 | /sankey-svgでの形 | 2ノード種別での形 |
| --- | --- | --- |
| ノード種別・配色 | `total/ministry/project-budget/project-spending/recipient` の5種、`TYPE_COLORS` | `section`（項）`project`（事業）の2種＋集約ノード（その他・未接続）に単純化 |
| 表示範囲の対象 | `offsetTarget: 'recipient' \| 'project'` | `offsetTarget: 'section' \| 'project'` に読み替え |
| 検索対象ノード | 省庁・事業・支出先を横断 | 項・事業の2種を横断（`nodesToSearch` の対象を絞るだけ） |
| フィルタ結果の集約表示 | 「その他の支出先」`showAggRecipient`、「その他の事業」`showAggProject` | 「その他の項」「その他の事業」に対応。オンオフはひとまず無し（常時集約）でもよい |
| 事業ソート | `projectSortBy: 'budget' \| 'spending'` | 事業側は当初予算額のみで統一。ソート切替UI自体を残すかは判断が必要（予算しか無いなら不要） |
| ミニマップの座標計算 | 4列レイアウト前提 | 2列（項｜事業）のレイアウトに合わせて作り直す |
| 詳細パネルのタブ | `panelTab: 'ministry' \| 'project' \| 'recipient'` | 項タブ・事業タブの2つ、または単一パネルに統合（現状の `/integrated-sankey` もタブ無しの単一パネル） |

## 不要（今回の方針では持ち込まない）

### 支出先（recipient）列に紐づくもの一式

- `pinnedRecipientId` / `filterRecipientName` `filterRecipientNameRegex` `debouncedFilterRecipientName`
- `topRecipient`（項/事業の2軸だけになるので、そのままの意味では不要。表示範囲の「もう一軸」は項に使う）
- `showAggRecipient`
- 支出先の検索結果アイコン（`getNodeColor` の recipient 分岐）

### 再委託（subcontract）関連

- `filterSubcontract` `filterRecipientIncludeSub` `maxSubcontractDepth`
- `subDepthEditing` `subDepthInput`
- 再委託フローの詳細ビュー一式（このタスクの対象外と既存ドキュメントにも明記済み）

### 事業の予算/支出の二重構造

- `project-budget` / `project-spending` の2ノード分割
- `scaleBudgetToVisible`（"事業の予算額を支出額に合わせて調整"）
- `filterMinSpendingText` `filterMaxSpendingText`（支出額のレンジ。RS事業側にあるのは
  当初予算額のみで、実支出額はこのファーストカットのデータモデルに無い）

理由：現在の `IntegratedProjectNode` は `linkedAmount`（MOF接続済み額）と
`initialBudget`（当初予算額）のみを持ち、実支出額を持たない。支出額ベースのフィルタ・
ソート・ノード分割は成立しない。

### 政策評価・AI関連

- `filterScoreO` `filterScoreX` `filterScoreN`（政策評価スコアの足きり）
- `scoreDialogItem` `scoreDialogLoading` とそのダイアログ
- AIチャットパネル一式（`showAiChat` `aiChatMessages` `aiChatSending` `aiChatProgress`
  `byokSettings` `chatSessions` `chatSessionId` 等）
- `policySummary` `policyError`

理由：`IntegratedProjectNode` に政策評価スコア・AI評価データは無い。将来
`/mof-sankey` 等と同様に持ち込む余地はあるが、今回のスコープ外。

### 省庁（ministry）列そのもの

- `pinnedMinistryName` `filterOnMinistryClick`（省庁ノードクリックでフィルタ）
- 省庁ノード自体の生成・配色・列位置計算

理由：方針で「項と事業ノードのみ」と明言されている。省庁は項の属性
（`ministry` フィールド）として残るが、独立した列・ノードにはしない。

### 年度切替

- `YearSelect`（2024年度⇄2025年度のRS年度切替）

理由：現在の結合データは「RS2025年度×MOF2024年度」の1組合せに固定されている
（`docs/integrated-sankey-graph-model.md`）。複数年度の結合データが無いため
切替先が無い。将来の拡張として復活させる余地はある。

### 目エッジ関連（今回の明示的な指示）

- 目エッジの個別描画・束ね/非束ねの議論そのもの
- 目名でのフィルタ（`itemQuery`。目そのものが無いので成立しない）
- 目の一覧・目単位の接続状態表示は、**事業詳細パネルの内訳**としてのみ残す
  （既存の「MOF接続済み／MOF未接続」バッジ表示は維持してよい。これはノード間の
  エッジではなく、選択した事業の予算内訳の一項目として表示するもの）

理由：ユーザー指示により、項↔事業を目エッジ経由ではなく直接結ぶ設計にする。
帯の金額はおそらく「その項からその事業への接続額（旧・目エッジのrsAmount合計）」を
エッジ1本に集約したものになる。目の個別内訳はホバーではなく詳細パネル送りにする。

## 未確定・要確認事項

実装着手前にユーザー確認が要ると考えられる点。

1. **項↔事業の帯の金額**：目エッジを廃するなら、帯の値は「その項からその事業への
   接続額の合計」になるはず（旧実装の目別エッジをsource×targetで合算したもの）。
   これでよいか。
2. **RS未接続・超過ノードの扱い**：目エッジが無くても「MOF項の目金額のうちRS事業に
   繋がらない残差」という概念自体は項の属性として残せるが、目単位の内訳が無いと
   「どの目が未接続か」を事業側で説明できなくなる。RS未接続ノードへのエッジも
   項単位の残差1本にする、で合っているか。
3. **表示範囲の共有スライダーへ戻すか**：前回実装は項・事業に独立した2本の
   `RangeWindowRow` を常設したが、`/sankey-svg` の実際の形は「対象コンボ＋共有
   1本」。「そのまま引き継ぎ」を優先するなら1本共有に戻す。2軸を同時に見たい
   実用上の理由があるなら独立2本のままにする、という判断が要る。
4. **事業ソート（予算順のみ）にUIを残すか**：データが当初予算額しか無いなら
   ソート切替コンボ自体が不要（常に予算順）だが、`/sankey-svg`の見た目を厳密に
   踏襲するなら空のコンボを残すという選択肢もある。実利がなければ省略を推奨。
5. **ミニマップを最初から作るか**：2列レイアウトなら図全体が縦に伸びるだけで
   横方向の見失いは起きにくい。ミニマップの実装コストに見合うか判断が要る。

## 実装順序の案（合意後）

1. グラフモデルを「項→事業」の直接エッジへ作り替える（`app/lib/integrated-sankey.ts`
   の目エッジ集計を項×事業の合算に変更。API・型はここが起点）
2. ノード種別・配色を2種＋集約ノードへ単純化
3. `/sankey-svg` の検索（ジャンプ）とフィルタ（絞り込み）を分離して移植
4. 表示範囲・ズーム・パン・ミニマップ・サイドパネル枠を移植
5. 事業詳細パネルに目内訳（MOF接続済み/未接続バッジ）を残す
6. Playwrightで `/sankey-svg` と並べて操作感を確認

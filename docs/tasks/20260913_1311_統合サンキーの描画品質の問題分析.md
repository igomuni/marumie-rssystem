# 統合サンキーの描画品質の問題分析

対象：`app/integrated-sankey/page.tsx`（Codexが実装、`f9fd9b6` 時点の描画ロジック）

Claude側は `data-testid` 3つの追加と波括弧1つの修正のみで、レイアウト・配色・描画には触れていない。
本書は実画面（1920×1080）と実装コードから見た問題の整理であり、修正指示ではない。

## 結論

見た目の粗さは配色やフォントの問題ではなく、**サンキー図として成立していないこと**が原因。
根本は次の2点で、ここを直さないと表層を整えても読めるようにならない。

1. 金額を平方根でスケールしている（帯の太さ＝金額という前提が崩れている）
2. エッジをノードの**中心**に接続している（帯の積み上げが無い）

## A. サンキーとして成立していない

### A-1. 平方根スケール（最重要）

```ts
// ノード高
const h = Math.max(12, Math.sqrt(Math.max(1,n.value))/total*(H-nodes.length*8-80));
// エッジ幅
const width = Math.max(1.2, Math.min(42, Math.sqrt(e.value/1e8)*1.6));
```

サンキー図の意味は「帯の太さ＝金額」「ノード高＝流入出の合計」であり、線形でなければならない。
平方根では429兆円と1兆円の比が 429:1 ではなく 20.7:1 に圧縮される。
図が金額の大小について嘘をつくうえ、**ノード高とそこに接続する帯の合計が一致しない**ため、
帯がノードからはみ出したり隙間が空いたりする。上限 `Math.min(42,...)` も大口を頭打ちにしている。

面積・長さの知覚補正として平方根を使う流儀はバブルチャートの半径の話で、サンキーには当てはまらない。

### A-2. エッジがノード中心に集まる

```ts
d={`M${a.x+layout.w},${a.y+a.h/2} C... ${b.x},${b.y+b.h/2}`}
```

始点・終点とも `y + h/2` 固定。本来はノードの縦方向に帯を順に積み上げ、
各帯が自分の太さ分だけオフセットを持つ。中心固定だと、1ノードに繋がる全帯が一点に収束するため、
実画面のような蝶ネクタイ状の束になり、どの帯がどこへ行くのか追えない。

### A-3. 最小高12pxの下駄で高さ合計が破綻

`Math.max(12, ...)` を各ノードに掛けたうえで `y += h+8` と積むため、ノード数が増えるほど
合計高が割当領域 `H - nodes.length*8 - 80` を超える。右列は下へあふれる。

## B. 画面に収まっていない

### B-1. viewBox と実際の高さの不一致

```ts
const H = Math.max(1050, Math.max(view.left.length, view.right.length)*30+80);
// viewBox="0 0 1560 1050"、transform は translate(pan.x, pan.y+150) scale(0.8)
```

上位35件表示なら `H = 35*30+80 = 1130` だが viewBox の高さは 1050 固定。
さらに +150 の下方向シフトが掛かるため、最下部が確実に切れる。
実画面では最大ノードである `RS未接続`（429兆円）が下端から見切れていて、
**図の中で最も金額の大きい要素が読めない**。

### B-2. 初期倍率と「全体」ボタンが内容に合っていない

`scale` 初期値 0.8、`translate(+150)` はいずれも固定値で、内容の実サイズを見ていない。
「全体」ボタンも同じ固定値へ戻すだけなので、はみ出しからの復帰手段が無い。
本来は内容のバウンディングボックスから fit する。

## C. 情報設計の問題

### C-1. ヘッダの数値と図の数値が対応しない

ヘッダは `data.metadata`（全データ）の 548.61兆／119.37兆／429.29兆 を出す。
一方 `RS未接続` ノードの高さと詳細は**表示中の上位N項に由来する分だけ**の合計。
読み手は同じ「RS未接続」という語で違う数を見せられる。

### C-2. 左列に「その他」が無い

右列には `その他のRS事業` 集約があるが、左列は `slice(0, limit)` で
上位N項の外が**消える**。落ちた項の金額はどこにも現れず、内訳へも到達できない。
仕様書の「集約されたエッジや『その他』を選択した場合、内訳へ到達できること」を満たしていない。

### C-3. 並び順と高さの基準がずれている

左列は `s.amount`（MOF項の総額）でソートし、高さは表示中エッジの合計で決めている。
上から大きい順に並んでいないように見える箇所が出る。

### C-4. 色に意味の衝突がある

- 左列：一般会計 `#317d52`（緑）／特別会計 `#456d9c`（青）
- 右列：RS事業 `#d8873b`（橙）

`/sankey-svg` では緑＝予算、橙＝支出という既存の意味づけがある。ここで緑を会計区分に流用すると、
2画面を行き来する読み手の学習を壊す。加えて画面の面積の大半を占めるのは
灰色（`#aab0aa`）の未接続帯で、**最も情報量の少ない要素が最も目立つ**。
凡例も無いため、色が何を指すか画面から判断できない。

## D. 実装の細部

| 箇所 | 問題 |
| --- | --- |
| 列見出し | `<div className="ml-[850px]">` のHTML絶対位置。列はSVG座標なので、ズーム・パンで即ずれる。実画面でも「RSの事業」が右列の上に無い |
| ラベル | 12pxの白文字を高さ12pxのノードに描くため、rectからはみ出し互いに重なる。背景が白のため読めない |
| `trim(name, 28)` | 幅230px・12pxフォントで収まるのは約19文字。28文字指定は必ずあふれる |
| ホバー吹き出し | 画面左下固定でカーソルから遠い。左列下部のノードを覆う |
| 詳細パネル | 右端に幅420pxで開き、**選択した右列そのものを隠す** |
| ヘッダカード | 左上に絶対配置で左列の先頭ノードに被る |

## E. 仕様書との乖離

仕様書は「`/sankey-svg` のLook、ズーム、パン、検索、選択、詳細パネルの操作感を基準として維持する」
「既存 `/sankey-svg` のTopN／表示範囲方式を再利用する」としていた。実装は
`/sankey-svg` の部品を使わず独自に書き起こしており、表示範囲UIも
`RangeWindowRows` ではなく3択のセレクトになっている。検索結果リストも無い。

`/sankey-svg` 側にはノード積み上げ・帯の配置・ラベル省略・凡例の実装がすでにあるので、
描画部分は複製元から持ってくるのが早いと考えられる。

## 優先順位の案

1. A-1（線形スケール）とA-2（帯の積み上げ）— ここだけで図の読みやすさは大きく変わる
2. B-1／B-2（内容に合わせたviewBoxとfit）
3. C-1／C-2（数値の対応と左列の「その他」）— 数の正しさに関わる
4. C-4・D（配色・凡例・ラベル・パネル配置）

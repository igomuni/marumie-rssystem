# Pipeline V2 基盤整備 実装タスク

## 目的

現在のデータパイプラインはそのまま維持し、比較・回帰確認用の Pipeline V1 として凍結する。

その横に、新しい Budget Flow および将来の予算イベント可視化の基盤となる Pipeline V2 を新設する。

今回のPRでは `/budget-flow` ページや既存 Integrated Sankey の表示ロジックは変更しない。

最優先事項は、

1. 公式取得データ（raw）
2. 原典別正規化データ（normalized）
3. 意味解決・統合データ（derived）
4. アプリ向け成果物（products）

を明確に分離し、2024年度データで再現可能なパイプラインを構築すること。

---

## 1. 基本原則

### Pipeline V1を壊さない

既存の以下の処理は原則変更しない。

- 現在の `download/RS_2024` 等
- `generate-mof-*`
- `generate-mof-rs-kou-moku-linkage`
- `generate-sankey-svg-*`
- `app/lib/integrated-sankey.ts`
- `/api/integrated-sankey`
- 既存 Integrated Sankey UI
- 既存 `public/data/*` の生成規則

Pipeline V1 は、新Pipelineの正当性を検証するための比較基準として残す。

Pipeline V2からV1の中間生成物を入力として利用しない。
V1からV2も参照しない。

## 3. download層

`data/download` は公式原本の保存場所とする。

### RS

`data/download/rssystem.go.jp/download-csv/2024/`

公式CSVを原則そのままのファイル名で保存する。

行政事業レビュー資料は、`data/download/rssystem.go.jp/sheets/2024/digital-agency/` のように、RSシステム上の公開URL構造に対応させる。

### MOF

`data/download/mof.go.jp/archive/2024/`（bb.mof.go.jp/archive/reiwaN.html。予算書・決算書のCSV/PDF。URLに`fy`が無い）
`data/download/mof.go.jp/account/fy2024/`（www.mof.go.jp/.../account/fy{year}/。決算の説明PDF）

を公式原本のルートとする（ディレクトリ名はソースURLの表記にそのまま合わせる。`budget/`はURL上に該当ページはあるが
ダウンロード対象データが無いため現時点では作らない）。

### download層で禁止すること

- カラム名変更
- 金額変換
- JSON化
- データ統合
- MOF/RS間リンク
- 名称正規化
- 項コード同一性判定
- ファイル内容の加工

「取得した原本」を可能な限りそのまま保存する。

---

## 4. normalized層

公式原本を、原典ごとに扱いやすい構造へ変換する。この段階ではMOFとRSを結合しない。

```text
data/normalized/
├── mof/
│   └── 2024/
│       ├── budget-items.json
│       ├── settlement-items.json
│       └── events.json
└── rs/
    └── 2024/
        ├── projects.json
        ├── budgets.json
        ├── expenditures.json
        └── requests.json
```

normalizedデータには必ずsource provenanceを残す。

```json
{
  "source": {
    "domain": "rssystem.go.jp",
    "dataset": "download-csv",
    "year": 2024,
    "file": "..."
  }
}
```

可能であれば元行を追跡できる情報も保持する。

---

## 5. fiscalYear と sourceYear を混同しない

RS 2024データには、2023年度実績、2024年度当初予算、2025年度要求などが同時に含まれ得る。

したがって、

```text
sourceYear = 2024
fiscalYear = 2025
eventType = request
```

のようなデータを許容する。「RS 2024 = fiscalYear 2024」と仮定してはいけない。

---

## 6. Budget Event

V2では金額を静的な1レコードへ潰さず、可能な限りイベントとして表現する。

当面想定するeventType：

- request
- government_draft
- initial
- supplementary
- reserve
- transfer
- carryover_in
- execution
- carryover_out
- settlement
- unused

ただし今回のPRですべてを完全実装する必要はない。

2024年度PoCでは最低限、MOFの initial / supplementary / settlement、RSの initial / execution / next-year request を扱えることを目標とする。

将来のeventTypeを追加可能な型設計にする。

---

## 7. EntityとEventを分離

MOFの「項」や「目」を、年度内で永久不変のIDとは仮定しない。

以下のような事象が存在するため：

- 項コード変更
- 名称差
- 補正による新設
- 所管変更
- 行政移管
- 移替
- 前年度繰越

したがって、`BudgetEntity` と `BudgetEvent` を分離する。

BudgetEventは必ず原典上のidentityを保持する。canonical identityへの統合はderived層で行う。

---

## 8. derived層

ここで初めて複数原典間の意味解決を行う。

```text
data/derived/2024/
├── budget-entities.json
├── budget-events.json
├── identity-resolution.json
├── project-links.json
└── transfer-links.json
```

identity-resolutionでは、exact match / normalized name match / code change / transfer relation / administrative transfer / unresolved など、どのルールで同一性を判断したかを記録する。

可能であればconfidenceまたはmatchMethodを持たせる。推測による強制統合は避ける。

---

## 9. products層

アプリケーション専用成果物はここから生成する。

```text
data/products/
├── integrated-sankey/
│   └── 2024.json
└── budget-flow/
    └── 2024.json
```

ただし今回のPRではBudget Flow用完成データを作り込む必要はない。

重要なのは、normalized → derived から integrated-sankey と budget-flow の双方を生成可能な構造にすること。

## 10. V1/V2比較検証

2024年度を基準年度とする。

```bash
npm run pipeline:v2:validate -- 2024
```

比較候補：

- MOF 当初 項数
- MOF 当初 金額
- MOF 補正後金額
- MOF 決算 項数
- RS事業数
- RS予算額
- RS執行額
- MOF目↔RS事業リンク数
- リンク済金額
- 未リンク金額

出力では MATCH / DIFF / V2_ONLY / V1_ONLY などを明確にする。

「一致すべき差分」と「V2の意味モデル変更による意図的差分」を区別できるようにする。差分を自動的に修正・吸収しない。

---

## 11. 重要な回帰テスト

1. MOF当初金額が原本と一致する
2. 補正予算の累積額を二重加算しない
3. 補正差額を正しくイベント化する
4. 一般会計・特別会計を区別する
5. RS sourceYear と fiscalYear を区別する
6. 翌年度要求額が正しいfiscalYearになる
7. rawファイルからnormalizedを再生成できる
8. normalizedからderivedを再生成できる
9. 同じ入力から同じ結果を生成する
10. Pipeline V1の生成物が変更されない

## 12. package.json

既存scriptを変更せず、新規コマンドを追加する。

```text
pipeline:v2:normalize:rs
pipeline:v2:normalize:mof
pipeline:v2:derive
pipeline:v2:validate
pipeline:v2:2024
```

`pipeline:v2:2024` で download済みraw → normalize → derive → validate まで一括実行できるようにする。

rawデータのネットワーク取得自体は別コマンドとして分離する。通常のbuild時に政府サイトへアクセスしてはいけない。

## 19. MOF「決算の説明」PDFの位置付け

Pipeline V2では、財務省「令和6年度 決算の説明」全体版PDF（`kessan_06_zenntaibann.pdf`）も公式raw原本として保存対象に含める。

配置例：

```text
data/download/mof.go.jp/account/fy2024/
├── kessan_06_zenntaibann.pdf
├── ...決算CSV/XML等の構造化原本
└── ...必要に応じた個別付表PDF
```

### 役割を3種類に分ける

#### A. 主データ

項・目、予算額、支出済額、繰越額、不用額など、構造化原本（CSV/XML等）から取得できるものは原則として構造化原本を主データとする。

PDF本文を主データの代替として全面的にパースしない。

#### B. 補助証拠・関係データ

構造化原本だけでは関係性を十分に説明できない以下の情報について、PDF本文・付表を一次資料として利用可能にする。

- 一般会計・特別会計の移替経費内訳
- 予備費使用額
- 繰越・不用に関する説明
- 予算編成から決算に至る経過
- その他、Budget Event / identity-resolution の根拠となる決算説明・付表

特に `transfer`、`reserve`、`carryover`、`administrative_transfer` 等のイベントや関係をderived層で生成する際は、根拠となったPDF・ページ・表・項目をprovenance/evidenceとして追跡可能にする設計を優先する。

#### C. validation / 検算

PDFに掲載される一般会計・特別会計等の総括値を、normalized / derivedデータの検算に利用できるようにする。

例：

```text
構造化原本 → normalized / derived集計
                         ↓
              決算説明PDFの総括値と比較
```

一致しない場合は自動補正せず、validatorで差分として報告する。

### Phase 1でやらないこと

- 506ページの全PDFを毎回フルパースすること
- PDF本文を項・目データの唯一のsource of truthにすること
- PDFの曖昧な文章から推測だけでBudget Entityを統合すること
- build時に財務省PDFをネットワーク取得・解析すること

必要な付表・表について段階的にparserを追加できる構造にする。

### source provenance例

```json
{
  "source": {
    "domain": "mof.go.jp",
    "category": "account",
    "fiscalYear": 2024,
    "file": "kessan_06_zenntaibann.pdf",
    "documentType": "settlement-explanation",
    "page": 0,
    "table": null
  }
}
```

ページ番号については、PDF物理ページと文書内印字ページの差があり得るため、可能なら両方を保持できる型にする。

### 設計原則

Pipeline V2では以下を区別する。

```text
構造化原本 = 主データ
PDF本文・付表 = 補助証拠 / 関係データ
PDF総括値 = validation
```

これにより、決算CSV/XML等の機械可読データを中心に再現可能性を維持しながら、移替・予備費・繰越などBudget Flowに必要な意味情報を財務省一次資料で補強できるようにする。

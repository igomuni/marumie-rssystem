## 観察（Fact）

### Q1 CONTEXT

- 69ブロックのすべてに CONTEXT 行がちょうど1行あり、どれも最初のデータ行より前にある。ブロックの途中で CONTEXT が切り替わることはない。
- CONTEXT は2種類だけだった。
  - **2桁コード（40件）**: すべて `所管` を含む（括弧付き17件、例: `19 内閣府所管（消費者庁）`）。
  - **4桁コード（29件）**: すべて `特別会計` を含み、そのうち9件は `勘定` も含む（例: `9808 財政投融資特別会計（投資勘定）`）。
- HIER 行があるのは4桁コードのブロック29件すべてで、2桁コードのブロック40件には1件もない。
- ページラベル（`文 1`・`復興特 1` など）は155件あり、そのうち7件は数字だけ。

### Q2 HIER（69件）

| コードの形 | 件数 | 観察 |
|---|---|---|
| 2桁・先頭0あり（`01` `05` …） | 27 | すべてブロックの1行目にあり、後続の `会計計` と同額 |
| 1桁（`1` `2` …） | 28 | 名称はすべて `勘定` で終わる。ブロック途中（直前が DETAIL）に15件ある |
| 2桁・先頭0なし | 14 | `10 食料安定供給`・`11 国有林野事業債務管理` はブロックの1行目（会計計と同額）。`31 復興庁`・`20 総務省`・`23 財務省` は先頭0ありの HIER の直後、またはブロック途中にある |

同じ「2桁 HIER」という書式に、会計名に相当する行（`01`、`10`）と府省名に相当する行（`31`）が混在している。先頭0の有無も、役割を区別する手掛かりにならない（`10`・`11` は会計名の位置にある）。

### Q3 CODE3 の字下げ

- **ページ内の字下げ段数**（その CODE3 があるページで、CODE3 の列位置が何種類あるか）: 1段 1,011・2段 401・3段 161・4段 25。ブロック単位の最大段数は、1段 57・2段 10・3段 1（env 000157016）・4段 1（env 000157010）。
- **CODE3 が DETAIL の下に入る例（`DETAIL_HAS_CODE3_BREAKDOWN`）**: DETAIL の金額が、直後に続く CODE3 の先頭からの合計と一致するものが37件（env 33・jinji 4）。例: env p18 は `030 原子力規制委員会`（5列目）→ `510 …共通費`（8列目）→ DETAIL 41（コード8列目）→ `005 …一般行政経費`（9列目）→ `001 / 003 / 006`（10列目）と並ぶ。
- **組織に相当する CODE3 と項に相当する CODE3 が同じ書式**: CODE3 のうち、後続の TOTAL と同額のもの（組織計 96・会計計 12）は、「直後の DETAIL の連続の合計と一致する」CODE3（1,060件）と同じ3桁書式で現れる。組織計と同額で直後に CODE3 が続く83件では、同じページ上で両者のコード列が**同じ列**のものが61件、組織側が浅いものが22件だった。国交省のように、同じ source の中でも両方の配置が出る。
- **同じ3桁コード値が、同じブロック内でページ内の段の異なる行に出る**: 84組。
- **同じコード値・同じ列で役割の異なる行もある**: 文部科学省の `010 文部科学本省`（組織計と同額）と `010 文部科学本省共通費`（直後の DETAIL 3件の合計と一致）は、どちらも5列目にある。

### Q4 DETAIL の親候補

- **Rule A（コード幅。HIER > CODE3 > DETAIL の順で、直前にあるより広い種別の行）**: 1,723件すべてで親候補が見つかり、すべて CODE3 だった。最寄りの CODE3 と DETAIL の間に TOTAL が挟まる例は0件。
- **Rule B（同じページ内で、字下げ列がより浅い直前の行）**: 親候補が見つからないものが774件、Rule A と食い違うものが202件。同じページ内でも、DETAIL のコード列は CODE3 の最浅列と同じ（60ページ）か、より深い（99ページ）かで揺れる。
- **最寄りの CODE3 が前のページにある DETAIL**: 112件。

### Q5 TOTAL（141件）

| TOTAL | 位置 | 加算関係 |
|---|---|---|
| 組織計 83 | ブロック末尾 11・次も TOTAL 29・次が CODE3 43 | 前の CODE3 と同額 78（うち2件はそのページで2段目の CODE3。単一の項の行が組織行と同額になる例）、前の DETAIL と同額 5 |

141件すべてで、閉じている範囲を加算関係から特定できた（範囲を特定できない TOTAL は0件）。TOTAL の並びは次のとおり。

- 2桁コードのブロック: `組織計×n（1〜12）> 所管計` が29ブロック、`組織計` 単独が11ブロック（内閣府の組織別ブロック）

### Q6 ページ境界（ブロック内で95か所）

- **境界をまたぐ行種別の並び**: CODE3>DETAIL 34・DETAIL>CODE3 23・DETAIL>DETAIL 18・CODE3>CODE3 11・TOTAL>CODE3 8・TOTAL>TOTAL 1。

- **CODE3**: 組織に相当する行・項に相当する行・DETAIL の内訳（目に相当する行）の3種類が、同じ3桁書式で現れる。上の Q3 のとおり。

## 解釈（Hypothesis。確定ではない）

- **コード幅だけで役割は決まらない**: CODE3 と HIER のいずれにも反例がある。
- **字下げだけで親は決まらない**:
  - 同じページ内で、組織と項が同じ列に並ぶ（61/83件）。
  - DETAIL と CODE3 の相対的な列位置がページによって揺れる。
  - ページ境界では列位置がずれる（80/95か所）。
- **CONTEXT＋行の順序＋TOTAL＋加算関係の組み合わせは、復元の候補として有望**:
  - CONTEXT の種別で、HIER の有無と TOTAL の並びが全件分かれる。
  - TOTAL の範囲は141件すべて加算関係で特定できる。
  - 項に相当する CODE3 の大半（1,060件）は、直後の DETAIL の連続の合計と一致する。
- **ただし残課題がある**:
  - env・jinji の「目」の段（DETAIL の内訳）の扱い
  - 金額が0の行や単一の子の行での縮退
  - ページをまたぐ状態の引き継ぎ（行の順序で扱える見込みだが未検証）

## 研究上の推奨

**evidence partially supports but ambiguity remains.** 字下げ単独の階層仮説は棄却される。CONTEXT・行の順序・TOTAL・加算関係を組み合わせる仮説を preregistration の候補とするかどうか、また env・jinji の目の段をスコープに入れるかどうかは、ChatGPT／ユーザーの判断に戻す。

## Post-P0 research decision

2026-10-11 に ChatGPT／ユーザーが確定した判断の記録。上の P0 の観察・件数・結論は変更していない。

### P0 の判定: GO

- GO は、字下げで階層を決める単純な仮説を採用するという意味ではない。字下げだけ、またはコード幅だけで階層を復元する仮説は、P0 で棄却された。
- `CONTEXT + 行の順序 + TOTAL の境界 + 抽出済み金額の加算関係` を組み合わせる方向は、次の仮説候補として検証する価値がある。
- 4択の評価は `evidence partially supports but ambiguity remains` のまま。

### H1 と H2 を分ける

- **H1 — Structural hierarchy reconstruction**: 意味ラベルを付けずに、論理行の間の親子関係だけを決定的に復元できるかを検証する。組織・項・会計・府省・目といったラベルは H1 では確定しない。
- **H2 — Semantic role labeling**: H1 が成立した後の別研究として、所管・特別会計・勘定・組織・項・目・要求経費などへの対応付けを検証する。
- H1 と H2 を、同じ実装・同じ評価の中に混ぜない。

### H1 の出力区分

| status | 意味 |
|---|---|
| `RESOLVED` | source の証拠と凍結した制約から、親子関係が一意に決まる |
| `AMBIGUOUS` | 候補が複数残り、一意に決まらない |
| `NO_PARENT` | 構造上の根などで、親がない |
| `NOT_APPLICABLE` | 親子関係の評価対象外 |

coverage を上げるために、`AMBIGUOUS` を `RESOLVED` に寄せることはしない。

### DETAIL → CODE3 は対象に含める

- 環境省・人事院で観察された `DETAIL └ CODE3`（DETAIL の内訳として CODE3 が続く構造）は、H1 の対象に含める。
- ただし、この CODE3 に `目` というラベルは付けない。目という役割の確定は H2 まで保留する。

### 否定条件（H1 preregistration で凍結する）

1. **字下げだけで親を決めない。** 根拠:
   - 組織と項が同じ列に並ぶ例がある（61/83件）。
   - DETAIL と CODE3 の相対的な列位置がページによって揺れる。
   - ページ境界で列位置がずれる（80/95か所）。
2. **コード幅だけで意味上の役割を決めない。** 根拠:
   - CODE3 は、組織・項・DETAIL の内訳のいずれにも同じ書式で現れる。
   - HIER は、会計名に相当する行にも府省名に相当する行にも同じ書式で現れる。
3. **金額の一致だけで親を決めない。** 根拠:
   - 子が1つしかない親は、子と同額になる。
   - 金額がすべて0の行（171行）では、多くの候補が同額になる。
   - 加算関係は、構造上の制約の一部としてだけ使う。

### H1 preregistration で決めておく事項

1. **precision には、独立した正解データ（GT）が必要。**
   - 制約に矛盾がないことを precision の代わりにしない。
   - H1 の実装前に、人がレビューした GT を凍結する。
   - GT の層には少なくとも次を含める:
     - 単純な CODE3 → DETAIL
     - 入れ子の CODE3
     - DETAIL → CODE3
     - HIER を含むブロック
     - ページをまたぐ親の引き継ぎ
     - 組織計
     - 所管計
     - 会計計
     - 金額がすべて0の行
     - 単一の子による縮退
   - 主指標は、GT 上で resolver が `RESOLVED` を出した関係の precision とする。`AMBIGUOUS` は precision の分母に入れず、coverage と曖昧率として別に評価する。制約違反も、precision とは別の指標にする。
2. **TOTAL の範囲は、複数の証拠がそろった場合だけ確定する。**
   - `RESOLVED` の候補にするのは、次がすべて成り立つ範囲だけとする:
     - 同じ CONTEXT・同じブロックの中にある。
     - 行の順序の上で連続している。
     - TOTAL の直前にある、構造上の候補範囲である。
     - 既知の TOTAL やブロック境界と矛盾しない。
     - 直接の子の候補が持つ7つの金額セルを合計すると、TOTAL と一致する。
   - 同じ条件を満たす範囲が複数あれば `AMBIGUOUS` とする。
   - 単一の子で同額であることは、それだけでは親の証拠にしない。P0 では、組織計が2段目の CODE3 と同額になる縮退を2件観察している。
3. **合計するのは直接の子だけ。**
   - 構造の検証でも金額の制約でも、加算するのは直接の子に限り、孫以下を重複して足さない。
   - `DETAIL └ CODE3` の場合、上位の親の合計に、DETAIL とその子の CODE3 を同時に加えない。
   - P0 で DETAIL の合計が CODE3 と合わなかった26件は、この入れ子構造に関係する。
   - これは特定府省の例外ではなく、H1 全体に適用する不変条件とする。
4. **重複ブロックは運用上は両方残し、主な precision では1つとして数える。**
   - 既知の重複は、環境省と経済産業省に重複掲載されている40行と30行のブロック。
   - 運用・source に忠実な指標（status の件数、coverage、曖昧率、source ごとの挙動）は、69ブロック全件を分母とし、重複も両方数える。
   - GT の主 precision では、block fingerprint が完全に同じブロックを1つの評価単位とし、同じ構造が precision に2回寄与しないようにする。必要なら、source で重み付けした precision を副指標として併記する。

### H1 の評価軸

1. GT に基づく resolved precision
2. coverage
3. 曖昧率
4. 制約違反率

precision と coverage は分けて扱い、`AMBIGUOUS` を誤答として数えない。制約の整合性を正解の代わりにせず、coverage を上げるための推測もしない。

### 次の段階: H1 — Structural hierarchy reconstruction preregistration + GT freeze

行うこと:

1. 仮説の正式な preregistration
2. resolver の入出力の契約
3. 制約の優先順位と、候補が並んだときの扱い
4. 評価指標
5. 層別の GT 抽出計画
6. 人がレビューした GT の作成
7. GT の凍結とハッシュの記録
8. STOP / GO 基準

resolver の実装はこの段階では行わず、GT と preregistration を凍結した後に別タスクとして行う。

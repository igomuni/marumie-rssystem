## 公開サイトに影響が出ているもの

### 1. `percentileRank` の同点バグ（app/lib/policy-evaluation.ts）

下限位置をそのまま順位に使っており、同点の塊が丸ごと最下位の帯に落ちる。AI採点は 0-10 を 0-100 に伸ばした離散値のため同点が大量に出る。

rs-vis で `buildPolicyEvaluations` を呼ぶ箇所は3つ（`app/quality/page.tsx`・`app/api/policy-summary/route.ts`・`app/lib/project-map.ts`）で、**公開サイトの推奨判断が実際にずれている**。marumie で midrank に直した際の変化:

```text
継続          2,127 → 2,245
要改善        1,522 → 1,515
条件付き継続   1,363 → 1,252
縮小            444 →   444
再設計          307 →   307
終了・廃止候補    31 →    31
```

最下位帯（終了・廃止候補）は 31件で不変。設計コメントが想定していた「5%で31件」の水準は保たれる。

**データ再生成は不要**。パーセンタイルは実行時に母集団から計算するため、`project-quality-scores-*.json.gz` は変わらない。コードだけ直せば出力が正しくなる。

### 2. 列名7件の不一致（scripts/generate-project-outcomes.py）

**当初 `effectAssessment` 1件と見たが、全列名を突き合わせた結果 7件だった。** 原因も「書き間違い」ではなく、**配布ZIPのヘッダと展開済みCSVのヘッダが別物**であることによる。

ZIP展開時に全角記号が正規化されている（2024・2025 の両方で同一の変換を確認）:

```text
－ (U+FF0D 全角ハイフン)  →  ー (U+30FC 長音)     ※本来 - であるべきところの誤変換
／ (U+FF0F)              →  / (U+002F)
（ ）(U+FF08/FF09)        →  ( ) (ASCII)
```

スクリプトの列名は配布ZIPのヘッダを書き写したもので、実際に読む `data/year_{YEAR}/` の展開済みCSVとは一致しない。不一致だった7列:

| 対象 | 影響を受けるフィールド |
|---|---|
| 4-1 | `effectAssessment`（`－`）、`reflection`・`reflectionDetail`（`／`） |
| 3-2 | 派生元・派生先の `種別`（`（）`）、派生元・派生先の `活動目標／成果目標`（`／`・余分な空白） |

現行の `rs2025-project-outcomes.json.gz` はこれら7フィールドすべてに値が入っている（`effectAssessment` 3,095件、`reflection` 5,034件、`logicModel.links` 5,758件で `fromKind`/`toKind` も充足）。つまり**コミットされているスクリプトはデータを生成した版に対する後退**であり、**このまま回すと7フィールドが黙って空になる**。

修正後は 2024・2025 の両年度で全列名が解決することを確認済み。あわせて、引けなかった列名をファイルごとに一度警告する `make_col()` を導入した（同種の後退を次から即座に検知するため）。

### 3. CSV数式インジェクション（scripts/export-luna-scores.ts・export-policy-decision-template.ts）

`=` `+` `-` `@` 始まりのセルを表計算ソフトが数式として実行する。引用符では防げない。生成物は `data/exports/` に commit されており、rs-vis はパブリックリポジトリのため、開いた人の環境で発火し得る。

# MOF × 概算要求の突合（M0〜M3）— 契約（案）

状態: **確定（ユーザーが §5 の 4 点を案どおりと確定）。この commit を事前登録とし、その後に実装・実行する。結果を見て規則を変えない。根拠は同日系列の Redesign Proposal（確定事項 §5）と Code System Inventory Result。

## 0. 入力と対にする版
- 概算要求: `data/work/budget-request-csv/{2024,2025}/{toc,total-table,detail-table}/sources/*.csv`（入力のディレクトリの SHA-256 の一覧を記録し、実行のたびに同じであることを確認する）。
- MOF: `tests/fixtures/mof-archive-csv/{version}/`。FY2024 は `2024`、FY2025 は `2025_teishutsu` と `2025` を**それぞれ**対にする（出力に `mof_version`）。
- 名称の比較は、空白（半角・全角）を除いた**完全一致**だけ。正規化・部分一致・読み替えをしない。金額は選択に使わない（診断のみ）。

## 1. 概算要求側の木（TOC を階層の根拠にする）
TOC の `区分` は階層の種類を明示している（`（所管）`、`（会計）`、`（組織）`、`（勘定）`、`（項）`、`（事項）`＝要求番号つきの \`NN‑NN 名称\`）。**項・組織・勘定・会計の識別は TOC の見出しだけで決める**（総表・明細表の \`CODE3\` の位置から推測しない）。
- 木: 各 PDF（source）の TOC を文書順に読み、見出しの直後の事項を、その見出しの子にする。事項は（要求番号, \`NN‑NN\`, 名称, ページ）を持つ。
- 事項の突き合わせ（TOC ↔ 明細表）: 同じ source で、明細表の \`DETAIL\`（要求番号, \`NN‑NN 名称\`）と TOC の事項を（要求番号, \`NN‑NN\`, 名称）の完全一致で結ぶ。一意に結べないものは、そのまま記録する。
- 目の所属: 明細表で、\`DETAIL\` の直後から次の \`DETAIL\`／\`CODE3\`（項・組織）／\`CONTEXT\` の直前までの \`CODE_5_4_2_4\` 行を、その事項の目とする。
- 総表との突き合わせ: 総表の \`DETAIL\`（要求番号, 名称）と TOC の事項を同様に結ぶ。金額は診断にだけ使う。
- TOC がない source、見出しの種類が上記以外のもの、は対象外として記録する（理由つき）。

## 2. 層
**M0 主体**: 概算要求の（所管／会計／勘定／組織）の名称、明細表の \`CONTEXT\` → MOF の所管・組織・特別会計・勘定。\`CONTEXT\` は第 1 ラウンドと同じ読み（一般会計は \`NN 〇〇所管…\` の〇〇、特別会計は \`NNNN 〇〇特別会計…\` の〇〇）。名称の完全一致。
**M1 項**: 概算要求の \`（項） NNN 名称\` → MOF の項。M0 で定まった主体の範囲で、項名の完全一致（コードは使わない）。一般会計は（所管, 組織, 項名）、特別会計は（特別会計, 勘定, 項名）で探す。
**M2 事項**: 概算要求の事項（TOC）→ MOF の事項。M1 で定まった MOF の項の中で、事項名の完全一致。\`NN‑NN\` の後半が MOF の主要経費別分類コードに一致するかを、裏づけの列（\`class_code_agrees\`）として記録する（不一致でも除外しない）。
**M3 目**: 概算要求の目（明細表）→ MOF の目。M1 で定まった MOF の項の中で、概算要求の目の行を（主要経費2桁＋目的別3桁, 使途別／経済性質別＋使途別／財政法＋経済性質別＋使途別（\`X\` の桁数による読み。インベントリの H1／H3／H4）, 目別, 目名）の組で**集約**し（項内の複数の事項にまたがる目を足し合わせる）、MOF の目へ対応づける。比較は目名の完全一致と、コードの組の完全一致の両方を満たすもの（読みで表せない成分は比べない：特別会計の \`X\` が 1 桁のとき経済性質別は比べない）。複数の MOF 行に一致する場合は、すべて候補として記録し、絞らない。

## 3. status と出力
status は層ごとに次のいずれか（\`reason\` を必ず付ける）: \`MATCHED\`（MOF の候補が 1 つ）、\`AMBIGUOUS\`（2 つ以上。候補ごとに 1 行）、\`NO_CANDIDATE\`（名称が一致する MOF の候補がない）、\`PARENT_UNMATCHED\`（上位の層で対応がなく探していない）、\`OUT_OF_SCOPE\`（TOC がない等）。
出力（版ごと）: \`m0-entities.csv\`、\`m1-kou.csv\`、\`m2-jikou.csv\`、\`m3-moku.csv\`、MOF にだけあった行の \`unmatched-mof-{kou,jikou,moku}.csv\`（\`reason\` は、上位が未対応／その階層だけ概算要求になし／複数候補で未確定／対象外）、\`summary.json\`、\`manifest.json\`。置き場所 \`tests/fixtures/mof-budget-request-match/{2024,2025,2025_teishutsu}/\`。列は Redesign Proposal の案のとおり（概算要求側のキーと行、MOF 側のキーと行、status、候補数、\`name_exact\`・\`class_code_agrees\`・\`parent_matched\`、診断の金額）。

## 4. 確認と STOP

- 構造の自己整合（報告のみ）: M2 で MATCHED の事項の MOF の項が、M1 で MATCHED の項と一致するか。M3 で MATCHED の目の MOF の項が、M1 の項と一致するか。

## 5. 確定した 4 点（ユーザー、案どおり）
1. 概算要求の階層を **TOC の見出しだけ**で決める（案）／ 総表の位置も併用する。
2. M2 の \`NN‑NN\` 後半の一致を**裏づけの列のみ**にして除外しない（案）／ 一致を必須にする。
3. M3 の集約キーに目名を含める（案。名称が違う同コードの目は別の目になる）／ コードだけで集約する。
4. 候補が複数のものは**絞らず**記録する（案）／ 単一候補になるまで追加の手がかり（コード、ページの近さ）で絞る。

## 追補 A（記述 Budget Request Document Sets の結果を見たあとに書く。ユーザー確定: (c) → (a) の順）
実行結果（Matching Result）の後に、次の 2 点を追加する。**結果を見たあとに書く追補であることを明記する。** 既存の規則・出力は変えず、追補の結果は別に出力する。
- **(c) TOC のない source の記録（規則の追加ではなく、抜けを埋める）:** TOC を持たず、総表か明細表だけを持つ source（かつ (a) で TOC の source に付かなかったもの）のすべての行を、`request-no-toc.csv`（`request_source`・`doc`・`row_type`・`row_index`・`text`）に `OUT_OF_SCOPE`／`no_toc` として記録する。件数を `summary.json` に入れる。
- **(a) 文書セット:** 同じファミリー（source 名の末尾の数字（`_` `-` を含む）を除いた共通部分）の中で、TOC を持たない source S を、TOC を持つ source T に付ける。条件: S の総表／明細表の `CODE3`（コードと名称、空白を除いた完全一致）のうち 1 つ以上が T の TOC の項と一致し、そのような T がちょうど 1 つ。0 または 2 以上なら付けない。付いた S の総表・明細表の行は、T の木の突合に、数字の順（`_2`, `_3`, …）に連結して使う。付いた組は `sets.csv`（T, S, 一致した項の数）に出す。`request_source` は T のままにする。
- 回帰条件: 追補 A の前後で、付いた S を持たない T の m1〜m3 の行は、バイト単位で変わらない。

## 追補 B（NO_CANDIDATE の診断を見たあとに書く。ユーザー許可: 全角／半角の違いを一致として扱う）
診断（同日系列の NoCandidate Diagnosis Result）で、完全一致にならなかった近似 22 件がすべて全角／半角の違いだけだったため、**名称の比較に限り、次の幅の統一（width fold）を両側に適用する。** これは「名称は空白を除いた完全一致」の例外であり、それ以外の正規化・部分一致・読み替えは引き続きしない。
- fold: U+FF01〜FF5E（全角の ASCII 相当の字）を対応する ASCII（U+0021〜007E）に、U+FF61〜FF9F（半角のカナ・約物）を NFKC で全角に変える。そのうえで空白（半角・全角）を除く。NFKC を全体には適用しない（`Ⅴ` など、幅の違いでない互換文字は変えない）。
- 適用先: M0〜M3 のすべての名称の比較（所管・組織・特別会計・勘定・項名・事項名・目名、TOC と総表・明細表の事項の突き合わせ）。出力の名称の列も fold 後の文字列になる。
- 結果の読み方: 追補の前後で、`status` の変化（NO_CANDIDATE → MATCHED／AMBIGUOUS など）の件数を報告する。複数候補が新たに生じた場合も、絞らずに記録する。
- 回帰条件: 追補の前後で、MOF 側の行の id・コード列は変わらない。名称の fold により変化した行以外の `status` は変わらない。

## 追補 D（行の位置による階層の評価 Result を見たあとに書く。ユーザー確定: TOC のない source は組織を使わず、所管の範囲で項名を探す）
TOC を持たない source のうち**総表を持つもの**に限り、総表の行の並びから木を作り、M1〜M3 を同じ手順で行う。結果を見て規則を変えない。TOC を持つ source の結果は変えない（回帰条件）。
- **木（総表のみ）:** 項＝`CODE3` の次の行が `DETAIL` のもの（項-A）。事項＝その項に続く `DETAIL`（次の項の前まで）。勘定＝`HIER` の先頭が 1 桁のもの（勘定-A）。会計＝`HIER` の先頭が 2 桁のもののうち、名称が MOF の特別会計の名前と（幅の統一・空白除去後に）完全一致するもの（会計-A を MOF の特別会計名で絞る）。組織は使わない。
- **範囲:** 会計の種類・所管名は、その source（文書セットに付いた source を含む）の最初の明細表の `CONTEXT` から取る。`CONTEXT` がなければ、同じファミリーの他の source の `CONTEXT` が**すべて同じ**（種類と名前）ときだけそれを使う。決まらなければ対象外（`no_context`）。
- **M1:** 一般会計は（所管, 項名）で、組織を問わず MOF の項を探す（同じ項名が複数の組織にあれば複数候補＝`AMBIGUOUS` のまま残す。親が一意でなければ M2・M3 は `PARENT_UNMATCHED`）。特別会計は（特別会計, 勘定, 項名）。M2・M3 は TOC がある場合と同じ。
- **文書セット:** 明細表だけを持つ source（総表も TOC もない）は、同じファミリーで総表を持つ source のうち、`CODE3`（コードと名称）が項と一致するものがちょうど 1 つあるとき、その source に付ける（追補 A と同じ条件。付く先に位置による木を含める）。
- **出力:** `m1`〜`m3` の末尾に `hierarchy`（`toc`／`position`）の列を追加する。位置による木の行は `position`。`request-no-toc.csv` には、木を作れなかった source の行だけが残る。
- **回帰条件:** 追補の前後で、TOC を持つ source の m1〜m3 の行（`hierarchy` 列を除く）はバイト単位で変わらない。

## 追補 E（明細表の位置による階層の評価 Result を見たあとに書く）

- **木（明細表のみ）:** 項＝`CODE3` の次の行が `DETAIL` のもの（項-D）。事項＝その項に続く `DETAIL`（要求番号は明細表の列、`NN‑NN` と名称）。勘定＝`CODE1`。会計＝`CODE2` のうち先頭が 2 桁で名称が MOF の特別会計名に一致するもの。組織は使わない。

- 出力: `hierarchy` 列は `position_detail`。`request-no-toc.csv` には、木を作れなかった source の行だけが残る。
- 回帰条件: 追補の前後で、`hierarchy` が `toc`・`position` の行は、バイト単位で変わらない。
